\section{Functional Requirements}
Functional requirements define the specific features SmartExam is responsible. These features are run in sequence in our system. We start with pre-exam templates, then live proctoring, and finally submissions and grading. If any step fails, the entire proctoring chain breaks. These requirements are an expression of actual academic rules. They were made to enforce exam policies in a transparent and verifiable way. Table~\ref{tab:functionalrequirements}. Table~\ref{tab:functionalrequirements} contains the shortened list below. The following sections detail each requirement and map the requirements to their intended use cases on the exam day.

\textbf{User and Access Management Requirements:} SmartExam has 4 users roles: Administrator, Teacher, Invigilator, and Student. Strict separation is implemented, so that users only have access to the features they need \cite{rbac1}. Administrators handle accounts. Teachers can create exams, upload expected test cases and add students. Live sessions are watched by invigilators, but only active exams are attended by students. This role engine must be simple enough for non-technical lab coordinators to use so that they can quickly assign accounts, reallocate seats, or verify permissions when class enrollments change mid-semester.

\textbf{Planning and Scheduling of Examination:} A date for a lab exam is not sufficient \cite{eassess1}. Teachers can specify the duration, whitelisted apps, coding tasks and the test cases for evaluation. Each exam is fully customizable, for example a Python programming exam has different environment rules than a computer networking test. The system also maps workstation IP addresses to particular student accounts. The mapping of the seat to the computer ensures that students can only access the exam from their designated computer, thus preventing duplicate logins or access from personal computers.

\textbf{Monitoring and Supervision Requirements:} SmartExam makes the difference with standard testing platforms by monitoring workstations in real time instead of simply running a quiz \cite{mit_cbt}. The invigilator dashboard displays a live grid of student cards showing active processes and periodic screenshots. The system detects events like loss of focus, unapproved application launches, and screenshot capture attempts. Importantly, the system does not automatically penalize or lock students; it records these incidents for manual review and final decision of the invigilator.

\textbf{Submission and Evidence Requirements:} Programming exams produce student files that have to be secured \cite{integ1}. The client automatically saves the student's work every 10 seconds. When the exam timer expires, the client forces an automatic upload of all submission files. This prevents any post-exam modifications. The system also keeps an immutable evidence log with usernames, hardware IDs, focus history and running processes. This log provides a detailed audit trail for resolving grading disputes and verifying workstation activity during the exam.

\textbf{Reporting and Post-Examination Review:} Standard testing platforms often forget post-exam analysis. Teachers have to manually compile files, attendance lists and plagiarism reports \cite{elicit1}. SmartExam automates this and uses the QuestPDF engine to generate structured PDF reports. The documents compile attendance, incident summaries, and final results to help teachers with grade review and offer administrators straightforward audits for compliance and accreditation.

\section{Non-Functional Requirements}
Functional requirements specify the functional behavior of the system and non-functional requirements specify constraints on quality and rules for operation \cite{iso25010}. These are the qualities that make or break in a lab environment. A slow login wastes exam time, an insecure server risks data leaks, and a laggy dashboard hinders effective invigilation.

SmartExam is built on six essential quality attributes: security, reliability, usability, performance, maintainability, and data integrity \cite{iso25010}. Security secures user identity and logs monitoring. Reliability: Availability of system at time of exams is ensured. Usability ensures that students and invigilators can operate interfaces under time pressure. Performance: keeps login and telemetry response times fast. Each module can be updated independently thanks to maintainability. Timestamps and logs cannot be tampered with thanks to data integrity.

The platform is optimized for the constraints of university laboratories where workstations run Windows and are connected by a Local Area Network (LAN). The system has both cloud and LAN-only modes to allow for slow or unreliable internet access. To protect privacy, data access is strictly scoped; invigilators can only see screenshots of their assigned sessions, not all exams. Neon PostgreSQL provides point-in-time recovery for backup and restore. Hourly or daily database exports are available on local servers.

\section{Requirement Gathering Techniques Used}

For developing a system for educators and IT staff, we gathered requirements for the system with structured interviews, paper prototypes and two brainstorming sessions \cite{elicit1, sommerville}.

\subsubsection{Interview}
We interviewed university teachers and lab coordinators to identify pain points in current practical exam administration \cite{elicit1}. The interviews focused on major disruptions and reporting needs. Feedback consistently highlighted two recurring themes that drove our requirements: the vital necessity of live workstation monitoring, and the crucial need for structured post-exam evidence logs.

\subsubsection{Prototypisierung}
We showed users simple interface prototypes (login, dashboard, student screen, active exam screen, and submission view) before formalizing requirements \cite{sommerville}. Three changes were made due to feedback: adding a visual countdown timer to the student's submission screen, placing live alerts at the top of the teacher's dashboard, and displaying one question at a time to reduce distractions.

\subsubsection{Brainstorming Session 1: Academic Workflow}
Our first brainstorming session captured the lifecycle of high-stakes lab exams \cite{elicit1}. We analyzed manual tasks that take a lot of time and determined the prototype components to focus on. We therefore focused on exam configuration, role management, and workstation assignment. The workstation assignment feature prevents students from starting exams on computers other than the ones assigned to them.

\subsubsection{Brainstorming Session 2: Monitoring and Reporting}
In our second brainstorming session \cite{agile1}, we discussed monitoring, proctoring (including face recognition) and reporting. We talked about event logging and report designs that teachers like. We decided that face recognition should run during the pre-exam stage, proctor reports should be stored in the database and the final PDF report should contain attendance, violations and scores as a single document.
