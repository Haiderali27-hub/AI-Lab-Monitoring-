\section{Functional Requirements}
Functional requirements map out the specific features SmartExam must perform. In our system, these features run in a sequence. We start with pre-exam templates, move to live proctoring, and finish with submissions and grading. If any step fails, the entire proctoring chain breaks. These requirements reflect real academic rules. We designed them to enforce exam policies in a clear and verifiable way. \subsection{User and Access Management Requirements}
SmartExam maintains four user roles: Administrator, Teacher, Invigilator, and Student. We enforce strict separation so users only access their required features \cite{rbac1}. Administrators manage accounts. Teachers configure exams, enroll students, and upload expected test cases. Invigilators watch live sessions, while students only participate in active exams. This role engine must be simple for non-technical lab coordinators to use, allowing them to quickly assign accounts, reallocate seats, or verify permissions when class enrollments change mid-semester.

\subsection{Examination Planning and Scheduling Requirements}
Scheduling a lab exam involves more than just selecting a date \cite{eassess1}. Teachers configure duration, whitelisted applications, coding tasks, and evaluation test cases. Each exam is fully customizable; for instance, a Python programming exam requires different environment rules than a computer networking test. Additionally, the system maps workstation IP addresses to specific student accounts. This seat mapping ensures students can only launch the exam from their assigned computer, preventing duplicate logins or unauthorized access from personal devices.

\subsection{Monitoring and Supervision Requirements}
SmartExam differentiates itself from standard testing platforms by monitoring workstations in real time rather than just hosting a quiz \cite{mit_cbt}. The invigilator dashboard displays a live grid of student cards showing active processes and periodic screenshots. The system automatically flags events like focus loss, unapproved application launches, and screenshot capture attempts. Crucially, the platform does not penalize or lock students automatically; it logs these incidents for manual review and final decision by the invigilator.

\subsection{Submission and Evidence Requirements}
Programming exams generate student files that must be secured \cite{integ1}. The client auto-saves the student's work every 10 seconds. When the exam timer expires, the client forces an automatic upload of all submission files, preventing any post-exam modifications. The system also maintains an immutable evidence log containing usernames, hardware IDs, focus history, and running processes. This log provides a detailed audit trail to resolve grading disputes and verify workstation activity during the exam.

\subsection{Reporting and Post-Exam Review Requirements}
Standard testing platforms often overlook post-exam analysis, requiring teachers to manually compile files, attendance lists, and plagiarism reports \cite{elicit1}. SmartExam automates this process using the QuestPDF engine to generate structured PDF reports. These documents compile attendance sheets, flagged incident summaries, and overall results, assisting teachers in grade review and providing administrators with clear audits for compliance and accreditation.

\section{Non-Functional Requirements}

While functional requirements describe what the system does, non-functional requirements set quality constraints and operational rules \cite{iso25010}. In lab environments, these qualities determine success; a slow login wastes exam time, an insecure server risks data leaks, and a laggy dashboard prevents effective invigilation.

\subsection{Software Quality Attributes}

We design SmartExam around six core quality attributes: security, reliability, usability, performance, maintainability, and data integrity \cite{iso25010}. Security protects user identities and monitoring logs. Reliability ensures system availability during exams. Usability guarantees that students and invigilators can operate interfaces under time pressure. Performance keeps login and telemetry response times fast. Maintainability allows independent updates to modules, and data integrity ensures timestamps and logs remain untampered.

\subsection{Other Non-Functional Requirements}

The platform is optimized for university lab constraints, where workstations run Windows and connect via a Local Area Network (LAN). To handle slow or unreliable internet access, the system supports both cloud and LAN-only modes. To protect privacy, data access is strictly scoped; invigilators can only view screenshots for their assigned sessions, not all exams. For backup and recovery, Neon PostgreSQL provides point-in-time recovery, supplemented by hourly or daily database exports on local servers.

\section{Requirement Gathering Techniques Used}

To build a system tailored for educators and IT staff, we gathered requirements using structured interviews, paper prototypes, and two brainstorming sessions \cite{elicit1, sommerville}.

\subsubsection{Interviews}
We interviewed university teachers and lab coordinators to identify pain points in current practical exam administration \cite{elicit1}. The interviews focused on identifying major disruptions and reporting needs. Feedback consistently highlighted two recurring themes that shaped our requirements: the critical need for live workstation monitoring and structured post-exam evidence logs.

\subsubsection{Prototyping}
Before drafting formal requirements, we presented simple interface prototypes (login, dashboard, student screen, active exam screen, and submission view) to users \cite{sommerville}. Feedback prompted three changes: adding a visual countdown timer to the student's submission screen, placing live alerts at the top of the teacher's dashboard, and displaying one question at a time to reduce distractions.

\subsubsection{Brainstorming Session 1: Academic Workflow}
Our first brainstorming session documented the lifecycle of high-stakes lab exams \cite{elicit1}. We analyzed manual, time-consuming tasks and determined which prototype components to focus on. Consequently, we targeted exam configuration, role management, and workstation assignment. The workstation assignment feature prevents students from launching exams from unassigned computers.

\subsubsection{Brainstorming Session 2: Monitoring and Reporting}
Our second brainstorming session focused on monitoring, proctoring (including face recognition), and reporting \cite{agile1}. We discussed event logging and report designs preferred by teachers. We concluded that face recognition should run during the pre-exam stage, proctor reports must be archived in the database, and the final PDF report should consolidate attendance, violations, and scores into one document.
