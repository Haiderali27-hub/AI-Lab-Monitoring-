\section{Functional Requirements}

Functional requirements define the explicit services, interactions, and behaviours that the system must provide in order to satisfy stakeholder expectations. In the proposed AI-Driven Lab Exam Monitoring and Management System, these requirements are interconnected because a practical lab exam must move in a controlled sequence from configuration to execution, monitoring, submission, and reporting.

Another important characteristic of these requirements is that they reflect academic control as well as software capability. The purpose of the system is not only to automate routine work, but also to provide exam governance in a form that is transparent, auditable, and fair. The following requirements are therefore written in operational sequence.

\section{Non-Functional Requirements}

Non-functional requirements define the quality conditions under which the functional services must operate \cite{iso25010}. In a project concerned with secure and fair academic assessment, non-functional properties are not secondary. If the system is difficult to use, invigilators may ignore it during the exam. If it performs poorly, the dashboard may become operationally irrelevant. If it is insecure, confidence in the entire assessment process may decline. For these reasons, the proposed system must satisfy multiple quality dimensions simultaneously.

\subsection{Security}
The system shall secure all user accounts, active exam sessions, and sensitive data transmission. Authentication must be verified via JWT tokens, and physical access is restricted through workstation hardware binding (HWID) checks. All data in transit must be encrypted using standard TLS protocols to prevent unauthorized access or intercept attempts in the lab.

\subsection{Reliability}
The system shall ensure operational reliability and high availability during active examinations. Telemetry streams and workstation lockdown modules must operate consistently without memory leaks or application failures. The system should maintain a connection uptime of at least 99.9\% during scheduled exams to ensure uninterrupted student activity tracking.

\subsection{Usability}
The system shall provide an intuitive and user-friendly interface for students, teachers, and administrators. The student client interface must be straightforward to reduce student anxiety, while the React admin dashboard should offer clear, color-coded visual cards for monitoring focus timelines. System error messages and notifications must be descriptive and easy to interpret under time pressure.

\subsection{Performance}
The system shall respond quickly to all user actions, maintaining low latency for real-time telemetry updates. User logins, diagnostics, and exam launches must complete within 2 seconds. The WebSocket proctoring stream should transmit screenshot and focus event packets to the teacher's dashboard with less than 1 second of delay.

\subsection{Maintainability}
The system shall be easy to update, extend, and maintain by using a modular service architecture. The ASP.NET Core REST API, React web panel, and WPF desktop client must follow clean separation of concerns. All code repositories should be well-documented, allowing subsequent development teams to integrate new features or adjust rules easily.

\subsection{Privacy}
The system shall protect the privacy of all candidates by restricting access to captured telemetry. Webcam baseline references, screenshots, and focus logs must only be accessible to authorized instructors and system administrators. The system must comply with data protection principles, automatically deleting or archiving monitoring media after the grade appeal period expires.

\subsection{Compatibility}
The system shall work reliably within standard university computer lab settings and operating systems. The student client must be compatible with Windows 10 and Windows 11 environments, which are typical for academic workstations. The React web dashboard should run seamlessly across modern browsers, including Google Chrome, Mozilla Firefox, and Microsoft Edge.

\subsection{Backup and Recovery}
The system shall backup and recover all exam progress data to prevent loss in the event of hardware or network failures. Student answers must be auto-saved locally in an encrypted cache and synchronized to the database every 10 seconds. In case of workstation power loss, the student should be able to resume the exam from the last saved state upon logging back in.


\section{Requirement Gathering Techniques Used}

The requirements for the proposed system were gathered through a multi-perspective process because lab examination problems are operational, academic, and technical at the same time \cite{elicit1}. No single elicitation technique could capture the full picture. The project therefore used interviews, prototyping, and brainstorming sessions to define realistic requirements.

\subsection{Interviews}

Interviews are a direct requirement elicitation technique in which stakeholders are asked structured questions to explain their current workflow, difficulties, and expectations. In this project, semi-structured interviews were conducted with a total of 8 academic stakeholders, including 5 lab instructors, 2 course coordinators, and 1 system administrator, to understand how practical examinations are scheduled, managed, and audited in standard university lab facilities.

To elicit precise operational requirements, the following key interview questions were presented:
\begin{enumerate}
    \item \textit{What are the most common methods students use to circumvent surveillance or collaborate during a programming assessment?}
    \item \textit{How do you verify that a student sitting at a computer terminal is actually the candidate registered for that seat?}
    \item \textit{What is the manual overhead involved in collecting, compiling, and grading source code files across multiple lab sections?}
    \item \textit{What specific live telemetry (e.g., screen captures, focus logs, process lists) do you need on your console to coordinate proctoring effectively?}
\end{enumerate}

The outcomes of these interviews were clear and actionable. First, the feedback highlighted the necessity of a physical workstation lock via hardware binding (HWID) to prevent students from sharing credentials or using unauthorized laptops. Second, it confirmed that live, real-time telemetry (focus tracking, webcam state, process logs) streamed over WebSockets is essential for immediate invigilator alerting rather than only post-exam logging. Third, stakeholders emphasized that final grades, attendance, and violation event logs must be consolidated into a single, downloadable PDF report to provide a complete, legally auditable academic record of the session.

\subsection{Prototyping}

Prototyping is a requirement elicitation technique in which early interface sketches or mock workflows are shown to stakeholders so that hidden usability issues can be discovered before full implementation. In this project, interactive wireframes and mock screens were developed for both the student-facing desktop client and the teacher-facing web panel, mapping directly to our core functional modules.
\begin{itemize}
    \item \textbf{Student Client Prototypes:} Mock designs for the login window (featuring HWID binding states), the pre-exam system verification checks (webcam, microphone, and background process scanning checklists), and the locked fullscreen exam workspace.
    \item \textbf{Teacher Web Panel Prototypes:} Mock layouts for the live proctoring grid (visual status cards representing individual students), the allowed applications whitelist configurator, and the Docker compile-sandbox execution details.
\end{itemize}

A key prototype evaluation session was held with 3 lab instructors to refine the layout flows. The feedback from this session led directly to two major usability refinements. First, the complex diagnostics dropdown menu was simplified into a single-click automated check to minimize student confusion before launching the locked exam environment. Second, the live proctoring dashboard was updated to include color-coded student cards (green for active, yellow for minor warnings, red for critical violations) with visual timeline charts, preventing cognitive overload when invigilators supervise large classes of up to 40 concurrent terminals.

\subsection{Brainstorming Sessions}

Brainstorming is a collaborative elicitation technique in which team members discuss ideas, problems, and possible solutions in multiple sessions to identify realistic and prioritized system requirements. The project team conducted three dedicated brainstorming sessions, each focusing on resolving critical architectural dependencies and choosing suitable software wrappers for the final implementation:

\subsubsection{Session 1: Workstation Authentication and Seating Allocation}
This session focused on securing physical laboratory boundaries. The team discussed methods for mapping student registrations to specific workstations without collecting sensitive personal details, opting to generate motherboard/CPU Hardware ID (HWID) hashes dynamically at login to enforce seat-bound security.

\subsubsection{Session 2: Real-Time Telemetry Streaming and Network Load}
This session addressed the data transmission frequency during active exam monitoring. The team debated the choice between periodic HTTP polling and WebSocket channels, deciding on Kestrel-hosted SignalR WebSockets to stream compressed screenshot buffers and focus loss events, ensuring low latency without overloading the university lab's network.

\subsubsection{Session 3: Docker Sandboxing and AI Semantic Evaluation}
This session focused on automated post-exam evaluations. The team brainstormed security requirements for executing untrusted student code, resolving to instantiate isolated, temporary Docker containers for compile-runs. For subjective theoretical questions, the team chose to implement sentence-transformers models to calculate cosine similarity scores against reference answer keys.

\subsubsection{Overall Brainstorming Outcomes}
The overall outcome of these brainstorming sessions was the final prioritization of the development schedule into eight distinct sprints and the establishment of a robust security policy. It defined how telemetry and grading data flow across the system layers, ensuring that the WPF student client, Kestrel API server, Docker host, and React dashboard remain perfectly synchronized throughout the exam lifecycle.

\section{Time Frame}

The project time frame translates the Agile development plan into a structured schedule consisting of eight sprints. Each sprint lasts four weeks, allowing iterative development, review, and refinement while keeping the project aligned with academic deadlines.

This sprint-based schedule ensures continuous progress, regular supervisor feedback, and balanced development across all twelve modules of the proposed system. The final sprint focuses on integration and polishing so that the prototype is complete and academically presentable.
