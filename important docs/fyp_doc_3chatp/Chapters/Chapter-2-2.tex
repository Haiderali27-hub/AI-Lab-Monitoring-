\section{Functional Requirements}

Functional requirements map out the specific features SmartExam must perform. In our system, these features run in a sequence. We start with pre-exam templates, move to live proctoring, and finish with submissions and grading. If any step fails, the entire proctoring chain breaks.

Table~\ref{tab:functionalrequirements} presents the compact list. Each requirement makes more sense when placed in its actual exam-day context. The subsections below expand the major functional areas.

\subsection{User and Access Management Requirements}
SmartExam manages four user roles: Administrator, Teacher, Invigilator, and Student. We need strict role separation so that users only see the features they need to access \cite{rbac1}. Admins handle accounts. Teachers create exams and upload test cases. Invigilators watch live sessions. Students only sit for their active exams.

This role engine must remain easy to use for lab coordinators who are not technical. It must be simple to add accounts, reassign students, or verify permissions, especially when classes change mid-semester.

\subsection{Examination Planning and Scheduling Requirements}
Setting up a lab exam requires more than just picking a date \cite{eassess1}. Teachers must define durations, whitelisted apps, coding tasks, and expected test cases. Different courses need custom setups; a python programming exam is very different from a networking lab test. 

We also need to map seating. Multiple student sections often share the same computer lab. Seat mapping assigns each student to a specific computer IP address. This prevents students from starting the exam from personal devices or logging into duplicate sessions.

\subsection{Monitoring and Supervision Requirements}
Live monitoring is where SmartExam differs from standard online learning tools \cite{mit_cbt}. While standard platforms only host quizzes, SmartExam actively monitors the student's workstation. The teacher dashboard shows a real-time grid of student status cards, complete with active processes and screenshots.

We track events like focus loss, whitelisted app violations, and screen capture status. The system never locks or penalizes a student automatically. It flags potential cheating, leaving the final decision to the human invigilator.

\subsection{Submission and Evidence Requirements}
Practical programming exams produce files that must be secured \cite{integ1}. The client auto-saves the student's work every 10 seconds. When the timer runs out, the client forces a submission and uploads the files to the database. Students cannot change their code after this point.

We also keep a secure evidence log. Every submission links back to the student's HWID, their user account, and their focus history. If a student disputes a grade later, we can check exactly what occurred at that workstation during their exam.

\subsection{Reporting and Post-Exam Review Requirements}
Standard testing tools often neglect post-exam analysis. After a session ends, teachers have to look through scattered files, attendance lists, and plagiarism matrices manually \cite{elicit1}. 

SmartExam resolves this by using the QuestPDF engine to generate structured PDF reports. These reports contain attendance data, incident histories, and grading summaries. This helps teachers review grades and provides admins with clear audits for accreditation.

\section{Non-Functional Requirements}

Non-functional requirements set the quality rules and constraints for our system \cite{iso25010}. For lab exams, these details are vital. A laggy login screen wastes exam time, an insecure server leaks student data, and a confusing dashboard makes invigilators miss cheating.

\subsection{Software Quality Attributes}

SmartExam focuses on six main qualities: security, reliability, usability, performance, maintainability, and data integrity \cite{iso25010}.

Security is critical because we store student identities and monitoring logs. Reliability is equally important; we cannot have the server crash mid-exam. The system must also be easy to use under time pressure, and the modules must be maintainable so developers can update components without breaking others. Lastly, data integrity ensures that our timestamps and grade logs remain untampered.

\subsection{Other Non-Functional Requirements}

We also designed the platform for university lab constraints. Most workstations run Windows and connect via a local area network (LAN). Since internet access can be slow, the system must work in both LAN-only and cloud environments.

Privacy is a priority when handling student screenshots. We restrict data access by role. For example, an invigilator can only view screenshots for their current session, and students can only access their own results. To prevent data loss, Neon PostgreSQL provides point-in-time recovery, and local servers can run daily database exports.

\section{Requirement Gathering Techniques Used}

To design a system that works for teachers, invigilators, and IT staff, we used structured interviews, paper prototypes, and two brainstorming sessions \cite{elicit1, sommerville}.

\subsubsection{Interviews}
We interviewed teachers and lab coordinators to understand how they run practical exams today \cite{elicit1}. We focused on what causes the most disruptions and what reports they need after the exam.

The feedback was consistent. Everyone highlighted the lack of live screen visibility and organized post-exam evidence as major gaps. These interviews directly shaped our live dashboard and PDF reporting requirements.

\subsubsection{Prototyping}
We walked through simple interface sketches with users before writing formal requirements \cite{sommerville}. We showed them the login, dashboard, student client, and submission screens.

Based on user feedback, we made three changes. We added a larger submission countdown timer, placed live alerts at the top of the teacher's dashboard, and simplified the student view to show only one question at a time to reduce distractions.

\subsubsection{Brainstorming Session 1: Academic Workflow}
Our first brainstorming session mapped out the exam lifecycle from start to finish \cite{elicit1}. We debated which manual steps take the most time and what features to prioritize in our prototype.

We prioritized exam configuration, role management, and seating mapping. Mapping seating to workstation IPs was added because it ensures students can only launch the exam from their assigned computer.

\subsubsection{Brainstorming Session 2: Monitoring and Reporting}
The second session focused on proctoring, face recognition, and reporting. We discussed what events are worth logging and what report layouts teachers need.

We decided that face recognition must run before the exam begins, and all proctoring alerts must be saved in the database for later review. We also designed the final PDF report to consolidate attendance, violations, and grades in a single document.
