\chapter{FUNCTIONAL ANALYSIS AND MODELING}

Here, we take the raw requirements gathered from our stakeholders and translate them into functional models. For SmartExam, this step is vital. We are dealing with low-level Windows API hooks, real-time telemetry streams, and WebSockets. If we do not map the boundaries clearly, the system will fail under high load during a live exam. We use use-case tables and data flow diagrams to make sense of this complexity.

We split this chapter into two parts: Use Case Modeling and Functional Modeling. First, we outline user stories and use case tables to show how students, teachers, and admins interact with the system. Second, we present our Entity Relationship Diagram (ERD) and Data Flow Diagrams (DFDs) to show how data moves between the client and our ASP.NET Core backend.

\section{Use Case Modeling}

We use use-case modeling to define the system's scope from the end-user's point of view \cite{uml_systems_analysis}. It helps us focus on what SmartExam does before writing the code. This prevents scope creep and ensures the student client and teacher panel align during development.

We have three human actors (Student, Teacher, Admin) and one automated service (the AI grader). The student uses the WPF client to run checks, sit for the locked exam, and submit code. The teacher uses the web dashboard to create exams, whitelist apps, view live feeds, and override locks. Admins manage accounts and check audit logs. Figure~\ref{fig:usecase_diagram} shows the UML Use Case diagram for these roles.

Teachers manage configurations, monitor WebSockets feeds, and review grading. Admins handle user profiles and audits. This strict separation helps us enforce security constraints at the database and API level.

\subsection{User Stories}

We wrote user stories to keep the Scrum team focused on user value \cite{user_stories_applied}. We used these stories to plan our sprints and define our done criteria.

The user stories for the AI-Driven Lab Exam Monitoring and Management System are organized by actor roles, covering the entire lifecycle of an examination from setup to monitoring, submission, evaluation, and reporting:

\subsubsection{Student User Stories}
\begin{enumerate}
    \item \textbf{Authentication and HWID Binding:} As a student, I want to log in using my university credentials on the workstation client, so that my identity is verified and my account is locked to the physical machine for the duration of the exam.
    \item \textbf{Pre-Exam Diagnostics Check:} As a student, I want the system to check my webcam, microphone, screen capture permissions, and network status, so that I can resolve any technical issues before the exam timer begins.
    \item \textbf{Readiness Verification and Mock Test:} As a student, I want to take a short mock test, so that I can verify that my code compilation, workspace, and keyboard inputs work properly under locked conditions.
    \item \textbf{Active Exam Dashboard:} As a student, I want to view my scheduled exams, read invigilator instructions, and access my workspace, so that I can begin answering questions without manual confusion.
    \item \textbf{Lockdown Mode Enforcement:} As a student, I want the workstation client to restrict task-switching, disable system hotkeys (e.g., Alt+Tab, Windows Key), and block unauthorized background applications, so that I can focus entirely on the exam while demonstrating compliance.
    \item \textbf{Auto-Save and Session Recovery:} As a student, I want my typed answers and source code to auto-save to the server every 10 seconds, so that my work is protected if the client crashes or the workstation loses power.
    \item \textbf{Controlled Exam Submission:} As a student, I want to submit my completed work manually before the deadline or have the system force-submit my answers when the timer expires, so that my performance is officially registered for grading.
\end{enumerate}

\subsubsection{Teacher User Stories}
\begin{enumerate}
    \item \textbf{Exam Template Configuration:} As a teacher, I want to design exams by adding coding or theory questions, specifying durations, and uploading public and hidden test cases, so that the evaluation aligns with course standards.
    \item \textbf{Allowed Applications Configuration:} As a teacher, I want to define the whitelist of permitted desktop software (e.g., VS Code, Python interpreter) for each exam, so that students can access the tools necessary for their practical tasks.
    \item \textbf{Access Control and Seating Mapping:} As a teacher, I want to map student registrations to specific labs, IP address ranges, and seats, so that only scheduled candidates can start the exam from approved physical workstations.
    \item \textbf{Live Dashboard Monitoring:} As a teacher, I want to view a real-time grid showing student status cards with active focus timelines, webcam states, and running processes, so that I can supervise the lab class from my console.
    \item \textbf{Lockdown Violation Alerting:} As a teacher, I want to receive instant notifications when a student attempts to switch tabs, launch blocked applications, or bypass the webcam, so that I can inspect the situation immediately.
    \item \textbf{Manual Invigilator Overrides:} As a teacher, I want to pause a student's timer, extend their duration, or override a locked client, so that I can assist students facing verified hardware issues or emergency situations.
    \item \textbf{AI-Assisted Grading and Similarity Check:} As a teacher, I want the system to run auto-compilation of code submissions, run semantic similarity checks on theory answers, and flag intra-class plagiarism, so that I can evaluate responses quickly and fairly.
    \item \textbf{QuestPDF Report Generation:} As a teacher, I want to export a comprehensive PDF report containing student grades, timeline violation events, and AI feedback, so that I can review and archive the session results.
\end{enumerate}

\subsubsection{Administrator User Stories}
\begin{enumerate}
    \item \textbf{User Account and Role Management:} As an administrator, I want to create, update, or deactivate user profiles and configure role-based permissions, so that system access complies with institutional policies.
    \item \textbf{System Audit Logs:} As an administrator, I want to review read-only logs of critical system events, such as device unbinding overrides or credentials updates, so that I can ensure operational accountability.
    \item \textbf{Configuration and Database Upkeep:} As an administrator, I want to configure server settings, clean up stale media files, and monitor database performance, so that the platform remains stable during high-concurrency exams.
\end{enumerate}

These user stories cover all 12 modules of the AI-Driven Lab Exam Monitoring and Management System. By organizing them into sprints, we made sure the WPF client and the React web panel were built and tested in parallel.

\subsection{Individual Actor Use Cases}

We expand the user stories into formal use case tables below \cite{use_case_definition}. These tables define the preconditions, triggers, main flows, and exception paths for our seven core modules. All tables follow our project's double-hline layout format.

Table~\ref{tab:uct_auth_device} details the authentication flow. We use native Windows APIs to fetch CPU and motherboard details, creating a unique HWID binding. This ensures students cannot log in from personal laptops or swap workstations during the exam.

Table~\ref{tab:uct_pre_exam_check} shows the pre-exam check. The WPF client checks webcam connection, processes, and network latency. We also save a baseline face photo to S3 storage for live comparison later.

Table~\ref{tab:uct_lockdown_telemetry} outlines the workstation lockdown rules. We hook low-level keyboard events to block Alt+Tab and the Windows key, and scan for secondary monitors. Telemetry screenshots are compressed and uploaded at randomized intervals to save lab network bandwidth.

Table~\ref{tab:uct_exam_config} details how teachers set up exams. Teachers upload test cases for coding tasks, whitelist apps, and map students to specific lab IP addresses to block external logins.

Table~\ref{tab:uct_live_proctoring} shows how the live dashboard works. We stream focus logs and screenshots to the teacher panel via WebSockets. The UI highlights student cards with color-coded alerts (green for on-task, red for lock violations) for quick invigilation.

Table~\ref{tab:uct_compilation_evaluation} explains the automated grading flow. Student code compiles inside sandboxed Docker containers to prevent malicious loops from crashing the backend. Theory answers are compared against reference answers using a semantic similarity model.

Table~\ref{tab:uct_audit_report} describes our reporting module. We compile scores, HWIDs, and WebSocket violation logs into a JSON payload. We then call the QuestPDF layout engine to generate a styled PDF report for university records.
