\chapter{SYSTEM DESIGN}
\label{chap:system_design}

SmartExam has three parts: the WPF \texttt{Student\_Desktop\_App} on the lab workstations, the React \texttt{Admin\_Web\_Panel} for staff and students, and the ASP.NET Core \texttt{Backend\_API}, which keeps its data in PostgreSQL. This chapter gives the design of these parts in UML diagrams. Section~\ref{sec:structure_diagrams} shows their static structure in class, deployment and component diagrams, and Section~\ref{sec:behavioural_diagrams} shows their run-time behaviour in activity, communication and sequence diagrams. Most diagrams were drawn early in the project; where a figure differs from the finished code, the text says how the code works.

\section{Structure Diagrams}
\label{sec:structure_diagrams}
Structure diagrams show the static parts of a system: its classes, components and machines \cite[Annex~A]{omg_uml251}. Agreeing on them early let us build the client, panel and API in parallel.

\subsection{Class Diagram}
A class diagram shows classes, their attributes and their associations \cite{class_diagram_uml, class_diagram_sparx}. Figure~\ref{fig:class_diagram} shows the main classes of SmartExam with their attributes, operations and the multiplicity of each association. A \texttt{User} has a role, possesses at most one \texttt{DeviceBinding}, creates exams, attempts exam sessions and is linked to the \texttt{AuditLog} that logs its activities. An \texttt{Exam} contains questions with their test cases, lists its allowed apps, maps seats and tracks sessions; each \texttt{ExamSession} streams monitoring events and captures answers, and each \texttt{Answer} is scored by an \texttt{AiGradingResult} and compared in a \texttt{PlagiarismResult}. The figure shows the main classes only. In the code the keys are GUIDs, the role is a \texttt{UserRole} field of \texttt{User} instead of a \texttt{Role} class, the allowed apps are a JSON list on \texttt{Exam}, the seat is a \texttt{Workstation} of a \texttt{Lab} stored on the student's \texttt{ExamAssignment}, the device binding keeps only a hash of the HWID, and each audit row is sealed into a hash chain.

\subsection{Deployment Diagram}
A deployment diagram maps software onto machines and the links between them \cite[Cl.~19]{omg_uml251}, \cite{deployment_diagram_vp}. Figure~\ref{fig:deployment_diagram} shows the nodes of SmartExam. The Student Workstation Client runs the SmartExam WPF client on .NET~9 with its lockdown Windows API hooks, and the Teacher/Invigilator Terminal runs the React web panel. The Application Server Host runs the ASP.NET Core REST API and the SignalR hub, and it connects to the Neon PostgreSQL database through Npgsql on TCP port 5432 and to a Docker sandbox that compiles student code. In the code the WPF client uses REST only (port 5050; HTTPS in deployment) and has no WebSocket link; only the web panel opens a SignalR connection. Docker is driven through the \texttt{docker} command on the server, with a local MinGW compiler as a fallback when Docker is not available. There is no separate AI service node: theory answers are graded inside the API.

\subsection{Component Diagram}
Figure~\ref{fig:component_diagram} splits SmartExam into a client tier, a server tier and a data tier. The client tier holds the WPF desktop client (login, HWID binding, diagnostics, lockdown, telemetry, code editor and auto-save) and the React web dashboard (exam configuration, live monitoring grid, grading, report viewer and seating map). The server tier holds the ASP.NET Core REST API with its controllers, the SignalR hub, the Docker compiler service and a grading service, and the data tier is the Neon PostgreSQL database. In the code the desktop client talks to the API over REST only, reports come from the \texttt{AnalyticsController}, theory answers are graded by TF-IDF cosine similarity inside the API (not by sentence transformers), and the database has 29 tables, not 14.

Behavioural diagrams show run-time behaviour: steps, messages and state changes \cite[Annex~A]{omg_uml251}.

\subsection{Activity Diagrams}
An activity diagram shows a workflow with its decisions and parallel branches \cite[Cl.~15]{omg_uml251}, \cite{activity_diagram_vp}. A diamond is a decision, and a thick bar opens or closes steps that run at the same time.

Figure~\ref{fig:activity_diagram} shows the whole exam flow, from login to grading. After the email, password and workstation HWID are accepted, the pre-exam diagnostics repeat until they pass; then the lockdown hooks are enabled and the questions and session timer start. While the timer runs, the student writes and auto-saves answers while screenshots and telemetry are captured. After the timer expires or the student submits, the hooks are released and the answers are graded and checked for plagiarism before the scores are saved. In the code the diagnostics do not scan processes (the process check runs during the exam), and grading starts at each student's submission: code runs in a Docker or local sandbox against the test cases, theory answers are scored by TF-IDF cosine similarity with key terms, and plagiarism is found by comparing token fingerprints, not abstract syntax trees.

Figure~\ref{fig:activity_recovery} shows auto-save and session recovery. The figure draws a 60-second loop that posts the answers when the network is online and writes an encrypted local cache when it is offline; after a crash the cache is read and synced. In the code an edited answer is sent 10 seconds after its first unsaved change, and every change is also written within a second to an encrypted local backup (AES-256-GCM, its key protected by Windows DPAPI), online or offline. Saves that cannot reach the server wait in a queue and are sent again in order. When the client restarts, it merges the server's answers with the backup, keeps the newer revision of each answer and sends the ones the server has not confirmed.

\subsection{Communication Diagram}
A communication diagram shows the objects in one interaction and their numbered messages \cite[Cl.~17.9]{omg_uml251}. Figure~\ref{fig:communication_diagram} shows what happens when a violation is raised and a teacher responds. The student client sends telemetry (1, acknowledged in 1.1), the event is logged in the database (2) and a violation alert is pushed to the live monitor (3), and the teacher client and the live monitor exchange the status update (4, 4.1). The teacher then issues a command (5, 5.1), the session is updated in the database (6) and the command and its result reach the student client (7, 7.1). In the code the student client sends its telemetry to the REST API, not to the hub, and the teacher's command is a SignalR hub method, not a separate override service. Because the WPF client has no SignalR connection, it receives the command in the reply to its next heartbeat, within 10 seconds.

\subsection{Sequence Diagrams}
A sequence diagram shows the messages between participants in time order \cite[Cl.~17.8]{omg_uml251}, \cite{sequence_diagram_vp}. Time runs from top to bottom; an \texttt{alt} box picks one of its branches and a \texttt{loop} box repeats its steps.

Figure~\ref{fig:seq_login} shows student login with HWID verification. The WPF client reads hardware serials from Windows, computes the HWID hash and posts the email, password and HWID to the API, which loads the user, checks the password, then creates the device binding on a first login or compares the HWID with the stored binding. If everything is valid a JWT is returned and the exam dashboard opens; otherwise an error is returned and the client shows it. In the code the route is \url{/api/auth/student-login} and the \texttt{AuthController} does this work itself. The serials are BIOS, system disk and baseboard (not CPU and motherboard), and passwords are hashed with PBKDF2 (600,000 iterations), not BCrypt. A failed login or HWID mismatch returns 401 Unauthorized, not 403.

In the code logout also revokes the session's refresh tokens, and the \emph{Logout} button is on the dashboard, outside the exam window, so there are no hooks to release: they are released when the exam is submitted.

In the code the panel posts the exam to \url{/api/exams} on the \texttt{ExamsController} (there is no \texttt{ExamConfigController}), and an invalid question returns 400 Bad Request with a message.

Figure~\ref{fig:seq_audit} shows audit logging during a report export. The teacher requests a grades PDF, an audit row is inserted, the grading data is read, the PDF is built with QuestPDF and the teacher downloads it. In the code the \texttt{ReportExportService} builds the file first and then saves the audit row (\texttt{REPORT\_GENERATED}, with the file's SHA-256) together with the report record; the file is downloaded through a separate \url{/api/analytics/reports/{fileName}} request.
