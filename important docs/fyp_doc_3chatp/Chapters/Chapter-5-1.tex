\chapter{SYSTEM DESIGN}
\label{chap:system_design}

In the context of the AI-Driven Lab Exam Monitoring and Management System, system design marks a critical phase where the conceptual vision and requirements detailed in system analysis begin to take a structured, concrete, and implementable form. This stage focuses on thoughtfully outlining the software architecture of the entire platform, including its key components, modules, database wrappers, runtime execution blocks, and how they communicate with one another. It defines the technical blueprints of the platform and ensures that each part of the system aligns with student verification needs, invigilator supervision goals, academic grading standards, and strict system security constraints. By translating abstract user requirements and system boundaries into a tangible, organized framework, the system design phase serves as the technical foundation for a scalable, secure, concurrent, and maintainable software solution. Ultimately, system design bridges the gap between planning and development, guiding the project from logical definitions to physical prototypes.

\section{Structure Diagrams}
A structure diagram acts as a static blueprint that reveals how different components within a software system are organized, compiled, and connected. It provides a visual layout of the system’s architecture, making it straightforward to understand how each separate part contributes to the overall compilation and execution. In modern software engineering, structure diagrams illustrate the hierarchy, packaging, arrangement, and connections among database classes and physical servers, ensuring that they work together in a unified manner \cite{structure_diagram_techopedia}.

In the design of the SmartExam system, structure diagrams serve as essential tools for visualizing the static backbone of the application. They offer a high-level overview of how major database entities, service layers, controllers, client terminals, and remote database servers interact to deliver core functionalities like authentication, lockdown boundaries, and grading pipelines. By defining relationships and dependencies between compile-time components, structure diagrams streamline system design and ensure cohesive, concurrent development. Furthermore, by offering a clear and comprehensive depiction of the system's static framework, these models support effective communication among developers, administrators, and academic stakeholders, guiding the implementation of a stable, well-integrated prototype.

\subsection{Class Diagram}
A class diagram is a static UML structure diagram that outlines the structure of a system by showing its classes, their attributes, methods, and the relationships among objects \cite{class_diagram_uml, class_diagram_sparx}. It uses standardized block symbols to depict functional data entities, service logic controllers, and database access objects along with their fields and operations. These diagrams simplify complex object-oriented software by breaking it down into manageable components. Each class serves as a blueprint for instantiating runtime objects, ensuring code reuse, type safety, and encapsulation. Relationships between classes, including inheritance, associations, aggregations, dependencies, and cardinalities, are explicitly defined. This allows developers to anticipate structural bottlenecks, enforce object-oriented design patterns, and maintain referential integrity throughout the development lifecycle.

\subsection{Deployment Diagrams}
A UML deployment diagram visually represents the physical architecture of a system, mapping out how software components are distributed across hardware devices, operating system nodes, and network segments during runtime. It shows where each executable component lives—whether it runs on a local workstation, a web browser, or a cloud server—and illustrates the communication protocols used to connect these nodes. This diagram is valuable for understanding how the physical infrastructure supports the system's operational requirements, highlighting the relationships between client devices, application servers, Docker hosts, and remote databases, which helps with resource allocation, security planning, scalability, and network maintenance.

The deployment configuration of the SmartExam system is shown in Figure~\ref{fig:deployment_diagram}, mapping out the runtime environments of the WPF student client, the React web dashboard, and the C\# ASP.NET Core backend:

The deployment topology mapped in Figure~\ref{fig:deployment_diagram} divides the platform into three main physical tiers. The Client tier includes the student workstation running the WPF desktop app, communicating with local Windows APIs for HWID retrieval and lockdown hooks. The Web tier includes the teacher's web browser rendering the React web panel. The Server tier includes the ASP.NET Core API server running on IIS or Kestrel, connected to a Neon PostgreSQL instance. Network links use HTTPS for REST API calls and WebSockets for streaming telemetry and live alerts, ensuring fast response times and robust security.

\section{Behavioral Diagrams}
Behavioral diagrams serve as dynamic blueprints that illustrate how a software system operates during its execution, showing how data moves, how states change, and how objects interact. These diagrams capture the interactions between system components, human actors, and external APIs, showing how information pipelines are executed \cite{behavioral_uml_diagrams}. They are essential for understanding the runtime functionality of software. For example, activity diagrams trace the control flow within a process, sequence diagrams map chronological message passing, and communication diagrams highlight collaborating objects.

Behavioral diagrams are valuable for analyzing the dynamic properties of the SmartExam platform. By illustrating how real-time data moves and how different components coordinate over time, they help identify potential latency issues, optimize data streaming, and verify that the system behaves correctly under concurrent conditions.

\subsection{Activity Diagrams}
An activity diagram in UML is a specialized flowchart that models the dynamic flow of control and activities within a system. Unlike simple flowcharts, activity diagrams capture granular processes, decision points, concurrent operations, and loops. They show how actions depend on one another, using swimlanes to separate responsibilities. By clearly showing how tasks are triggered, how conditions affect execution paths, and how final states are reached, activity diagrams help developers visualize business logic and user workflows \cite{activity_diagram_vp}.

The activity workflow for a student taking an exam on the SmartExam client is shown in Figure~\ref{fig:activity_diagram}:

The activity flow illustrated in Figure~\ref{fig:activity_diagram} maps the sequence of actions from when a student launches the client to the final submission. It starts with user login and HWID validation. If verification succeeds, the client starts system diagnostics, testing the webcam and checking running processes for blacklisted items. \subsection{Communication Diagrams}
UML communication diagrams provide a structured way to visualize object interactions within a system by focusing on the links and messages exchanged between objects. While similar to sequence diagrams, communication diagrams emphasize the structural relationships and routing paths among objects rather than their timeline sequence. Objects are connected by association links, and numbered arrows indicate the sequence and direction of message passing. These diagrams show how multiple components collaborate to fulfill a specific use case, helping developers verify object responsibilities and ensure that collaboration pathways are logically structured \cite{communication_diagram_boardmix}.

\subsection{Sequence Diagrams}
UML sequence diagrams are used to visualize the chronological flow of events and messages within a system, illustrating how components interact over time. They provide a timeline-based view, with lifelines representing participating objects and horizontal arrows representing messages or method calls. This structure helps developers track execution flows, trace API requests, identify latency bottlenecks, and design secure authentication patterns \cite{sequence_diagram_medium}.

In the SmartExam platform, sequence diagrams map the chronological communication between client interfaces, API controllers, authorization services, and databases, detailing core operational scenarios.

\subsubsection{Login}
The sequence diagram for student authentication and workstation hardware ID binding is illustrated in Figure~\ref{fig:seq_login}:

As shown in Figure~\ref{fig:seq_login}, the login sequence begins when a student enters their credentials on the WPF client dashboard. The client queries the workstation's motherboard and CPU IDs using native Windows APIs to generate a unique HWID hash. The client then sends a POST request with the email, password, and HWID to the auth controller. The controller validates the credentials and checks the device bindings table in the database. If no binding exists, the server binds the current HWID to the user account. If a binding exists, it verifies that the incoming HWID matches the registered hash. If they match, a JWT token is generated and returned to the client, allowing the student to access the exam workspace. If they do not match, the request is rejected with a validation error.

\subsubsection{Start Exam and Telemetry Ingestion}
The sequence diagram for starting an exam session and streaming background telemetry is illustrated in Figure~\ref{fig:seq_telemetry}:

The sequence diagram in Figure~\ref{fig:seq_telemetry} maps the chronological execution flow when a candidate launches an active exam workspace and initiates background telemetry streams. When the student clicks the start exam button, the WPF client activates native Windows API hooks to disable Task Manager and lock keyboard hooks (blocking shortcuts like Alt+Tab). The client then establishes a persistent WebSocket connection to the SignalR Hub. Once connected, a background logging thread starts running on the client, querying the operating system every 30 seconds for active process names, window focus handles, and compressed screenshot buffers. This payload is transmitted via WebSockets to the SignalR Hub. The server processes this telemetry stream and writes the logs to the \texttt{MonitoringEvents} database table. If the server identifies focus loss anomalies or unwhitelisted running applications, it immediately pushes a real-time WebSocket violation warning to the teacher's proctoring console, enabling live invigilator oversight.

\subsubsection{Docker Code Compilation}
The sequence diagram for executing and grading programming submissions inside isolated sandboxes is shown in Figure~\ref{fig:seq_compilation}:

As illustrated in Figure~\ref{fig:seq_compilation}, the code compilation sequence manages the secure execution of untrusted programming files submitted by candidates. When the instructor clicks the run evaluation button on the React dashboard, the web app transmits a POST request to the API server's grading controller. The server queries the database for student code answers and the corresponding exam's public/hidden test cases. Upon retrieving these records, the server calls the Docker Host Remote API to instantiate a sandboxed execution container. The server then copies the student's code and test case vectors into the isolated container and executes the compiler wrapper script. The container compiles the code, executes it against the test cases, and returns execution metrics (including test pass rates and execution duration) to the server. The server then issues a Docker command to stop and remove the container. Finally, the grading controller writes the scores to the \texttt{AiGradingResults} table in the database and returns a success confirmation to the teacher's web dashboard.

\subsubsection{AI Semantic Grading and Plagiarism Check}
The sequence diagram for executing semantic scoring and pairwise plagiarism checks is illustrated in Figure~\ref{fig:seq_ai_plagiarism}:

The sequence diagram in Figure~\ref{fig:seq_ai_plagiarism} outlines the post-exam grading pipeline which evaluates subjective responses and checks for code copying across the class. When the grading pipeline is triggered, the server queries the database for student theory answers and the teacher's reference answer keys. For each theory answer, the server sends a POST request to the AI Semantic Service. The microservice runs a sentence-transformers vector model to calculate cosine similarity scores between the student's text and the reference key, returning the similarity grade and semantic feedback to the server. Following semantic grading, the server queries all code submissions for the exam and invokes the Plagiarism Engine. The engine parses the code files into Abstract Syntax Trees (ASTs) and executes pairwise comparison algorithms to detect similarity metrics. The similarity indexes are returned to the server, which writes the aggregated scores and plagiarism flags to the \texttt{AiGradingResults} and \texttt{PlagiarismResults} tables.
