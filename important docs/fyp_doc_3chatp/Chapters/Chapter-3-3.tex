\section{Software Project Management Plan}

\subsection{Project Planning}

We plan in eight four-week sprints (Table~\ref{tab:timeframe}). Sprint 1 covers requirements and architecture, Sprints 2--7 deliver the modules, and Sprint 8 is for integration, testing and the demonstration. A task is done when its code and tests pass and its thesis section is updated. The work itself is broken down in the Work Breakdown Structure (WBS) of Section~\ref{sec:wbs} \cite{wbs1}, and the four plans below set the milestones, the documents, the resources and the quality checks.

\subsubsection{Documentation Plan}

The report and its sources are kept in step with the code:
\begin{itemize}[nosep]
    \item This report is written in LaTeX, and the section a task changes is updated in that task (R9).
    \item Diagrams are kept as text sources (PlantUML, and Graphviz for the critical path network) beside the report, so they are redrawn when the design changes.
    \item Each version of the report is recorded in the Revision History with its author and checker; supervisor feedback from the Sprint Review goes into the next sprint's backlog.
    \item The testing owner keeps the test catalogue in the code repository (Chapter~\ref{chap:testing}).
\end{itemize}

\subsubsection{Quality Plan}

Quality is checked inside every sprint, not only at the end:
\begin{itemize}[nosep]
    \item Each module is tested in its own sprint (the M2 and M4 tests, moved after the FYP-I review, were completed in Sprint 8): xUnit API integration tests, Playwright end-to-end tests for its web screens and unit tests for its desktop logic. The full regression suite is rerun after each group of fixes.
    \item Checks that need a real lab PC go on the manual lab checklist (Table~\ref{tab:st_pending}).
    \item AI output is advisory: the teacher reviews and can override every suggested mark, and no violation leads to an automatic penalty.
    \item The supervisor reviews each increment at the Sprint Review. Chapter~\ref{chap:testing} gives the test plan and the results.
\end{itemize}

\subsubsection{Critical Path Method}

The critical path is the longest chain of dependent activities; any delay on it delays the project \cite[Sec.~6.5.2.2]{pmbok6}. Table~\ref{tab:cpm} lists our activities and Figure~\ref{fig:criticalpath} shows the network.

The critical path is A $\rightarrow$ B $\rightarrow$ D $\rightarrow$ E $\rightarrow$ F $\rightarrow$ G $\rightarrow$ H $\rightarrow$ I, which takes 32 weeks ($8 \times 4$); the only other chain, through C, takes 30 weeks. Only C has float: it takes two weeks alongside B, so it can slip two weeks without moving the end date. Since almost all work is on the critical path, a late sprint delays every later one.

\subsubsection{Schedule Control}
\label{sec:schedule_control}

We track progress with sprint burn-down charts \cite{scrum1}. If less than 80\% of a sprint's story points are done at the review, we hold a recovery meeting and move or cut backlog items before the next sprint starts.
