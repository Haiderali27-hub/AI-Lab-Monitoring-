\section{Software Process Model}

The development of the AI-Driven Lab Exam Monitoring and Management System follows the Agile process model. Agile is particularly suitable for this project because the system contains several interdependent modules, requires continuous refinement of workflows, and must respond to user feedback related to usability, security, and academic practicality. In projects involving dashboards, access roles, examination rules, event logging, and post-exam reporting, it is difficult to finalize every detail correctly at the very beginning. Agile provides a controlled but iterative way to build the system in increments, validate assumptions early, and refine the product across repeated feedback cycles.

\subsection{Process Model Introduction}

Agile is an iterative and incremental development model in which software evolves through repeated short cycles called sprints. Each sprint focuses on a manageable subset of work and produces a meaningful improvement in the system. Rather than postponing user feedback until the final stage, Agile encourages continuous interaction between planning, implementation, review, and refinement. This makes it highly appropriate for academic systems where stakeholders often understand their needs more clearly after seeing early prototypes and working workflows.

In the context of the proposed system, Agile supports a practical balance between technical implementation and institutional feedback. An early sprint can validate whether the role-based dashboard structure is clear, while a later sprint can refine monitoring logic, face verification flow, or reporting outputs based on observed weaknesses. Such iterative evolution helps reduce the risk of investing too much effort in features that are technically complete but operationally unsuitable. It also helps the project remain realistic within semester constraints while still demonstrating meaningful progress.

\subsection{Justification of Proposing the Process Model}

The choice of the Agile process model is directly justified by the highly modular, sequential, and feedback-dependent structure of the AI-Driven Lab Exam Monitoring and Management System. Rather than attempting a monolithic development approach, the system's twelve core functional modules are distributed across eight distinct, iterative sprints. This iterative mapping ensures that complex, interdependent features are developed, tested, and integrated incrementally. For instance, establishing user roles and HWID-based device binding in Sprint 2 provides the necessary authentication foundation before configuring exam session templates in Sprint 3. Similarly, the secure WPF lockdown client designed in Sprint 4 serves as the operational host for the live telemetry services built in Sprint 5, which in turn feeds data into the submission, evaluation, and QuestPDF reporting modules developed in Sprints 6 and 7. This sprint-based progression allows each module to be validated against its functional dependencies before subsequent components are implemented, ensuring a stable, well-integrated prototype by Sprint 8.

Furthermore, this sprint-driven iterative approach is critical for accommodating the evolving requirements of an academic Final Year Project (FYP). Technical assessments in computer science computer labs involve a wide range of variables, from network latency and operating system constraints to user experience preferences of invigilators and students. A rigid, single-phase development model would assume all UI layouts, proctoring rules, and grading heuristics could be defined flawlessly at the outset. In contrast, dividing the project into 4-week sprints allows the development team to demonstrate operational increments to project supervisors and system administrators at regular intervals. Usability feedback on the live proctoring dashboard (Sprint 5) or the AI evaluation test case parser (Sprint 6) can be immediately integrated, preventing design flaws from propagating. Ultimately, this iterative methodology ensures that the final system is not only technically sound but also operationally practical and aligned with real-world institutional constraints.


\subsection{Steps of Process Model}

The Agile process model for this project is organized into eight sprints. Each sprint spans four weeks, which is treated as an approximately thirty-day working cycle for planning, implementation, review, and refinement. The twelve project modules are distributed across these eight sprints so that each increment produces a meaningful and reviewable outcome.

\subsubsection{Sprint 1: Requirement Analysis, Backlog Preparation, and System Planning}
This sprint is dedicated to requirement analysis, backlog preparation, and system planning for all twelve system modules. All initial activities in this cycle are mapped to outlining the scopes, boundaries, and dependencies of these modules prior to core development. Activities include stakeholder discussions, use-case mapping, product backlog preparation, initial architecture sketches, and project scope approval.

\subsubsection{Sprint 2: Authentication and Device Binding (Module 1) and User and Role Management (Module 7)}
This sprint is completely mapped to the development and integration of Authentication and Device Binding (Module 1) and User and Role Management (Module 7). All tasks within this four-week cycle are designed to build and secure these two core modules, establishing the system's foundational identity and authorization layer. Activities include designing login endpoints, HWID extraction libraries, user registration interfaces, role permission maps, and secure dashboard routing for administrators, teachers, and students.

\subsubsection{Sprint 3: Exam Creation and Configuration (Module 8) and Eligibility and Access Control (Module 9)}
This sprint is dedicated entirely to the implementation of Exam Creation and Configuration (Module 8) and Eligibility and Access Control (Module 9). The entire four-week schedule is mapped onto designing, building, and verifying these administrative modules to enable teachers to manage and restrict exam access. Activities include coding exam template interfaces, configuring allowed applications lists, setting test case definitions, exam seat assignment logic, and manual teacher eligibility overrides.

\subsubsection{Sprint 4: Pre-Exam System Verification and Mock Test (Module 2), Exam Dashboard (Module 3), and Secure Exam Environment Module (Module 4)}
This sprint is mapped to the simultaneous construction of the Pre-Exam System Verification and Mock Test (Module 2), Exam Dashboard (Module 3), and Secure Exam Environment Module (Module 4). All development tasks in this cycle focus on implementing and securing these client-side modules to form a robust student lockdown environment. Activities include designing the student WPF client, fullscreen locked mode (disabling Alt+Tab, Task Manager, Win keys), and automated client readiness verification checks.

\subsubsection{Sprint 5: Live Monitoring Client Service (Module 5) and Live Proctoring Dashboard (Module 10)}
This sprint centers on the creation and testing of the Live Monitoring Client Service (Module 5) and the Live Proctoring Dashboard (Module 10). The activities of this sprint are fully mapped to implementing these two modules, establishing real-time telemetry streaming and live classroom monitoring. Activities include developing client background focus tracking and process list logging, heartbeat synchronization protocols, and the live React grid timeline dashboard for instructors.

\subsubsection{Sprint 6: Exam Submission and Backup (Module 6) and AI-Assisted Evaluation Module (Module 11)}
This sprint is mapped to the deployment of the Exam Submission and Backup (Module 6) and the AI-Assisted Evaluation Module (Module 11). Every task in this sprint supports these two modules by implementing secure auto-save and submission channels alongside automated and semantic grading mechanisms. Activities include coding student answer auto-save systems, local encrypted backups, automated compilation and execution against test cases, AI theory evaluation, and plagiarism matrix comparison.

\subsubsection{Sprint 7: Logs, Analytics and Audit Trail System (Module 12)}
This sprint is dedicated to implementing the Logs, Analytics and Audit Trail System (Module 12). All activities within this period are mapped to this module, creating the database schemas, logging systems, and QuestPDF report engines required for secure auditing. Activities include setting up database transaction audit logs, logging focus-loss anomalies, computing exam statistics, and implementing QuestPDF layout engines for downloadable analytical exam reports.

\subsubsection{Sprint 8: System Integration, End-to-End Testing, Bug Fixing, and Final Document Polishing}
This sprint is mapped to the system integration, end-to-end testing, and final polishing of all twelve previously developed modules. The activities in this final cycle are focused on uniting these modules into a single cohesive platform, performing final bug fixes, and refining documentation. Activities include module integration, end-to-end user flow testing, UI polishing, sprint review closure, final documentation, and preparation of deliverables for demonstration.
