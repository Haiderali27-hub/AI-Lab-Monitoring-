\section{Software Process Model}

The SmartExam platform being a set of interconnected modules that are highly dependent on each other. Due to ongoing evolution and changes based on design review by supervisors and other stakeholders, a rigid development methodology like Waterfall is not an ideal option for this project. A model that can facilitate a flexible scope is preferred.

\subsection{Process Model Introduction}

The selected process model is Agile, more specifically we'll be utilizing a structure divided into multiple development cycles, or Sprints. During each Sprint, a potentially usable and demo-able chunk of the application is developed. This model proves efficient in projects where the overall project's scope is fluid and requirement changes are expected along with continuous stakeholders' feedback. The core strength lies in the incremental delivery which reduces risks and ensure the timely integration and validation of various project features. Unlike Waterfall, problems and mis-judgements are caught early within the cycle rather than at the end where it is costly to fix.

This type of development is especially fitting for SmartExam as features such as role-based access, HWID locking, live telemetry streaming, and automatic grade calculation need to be tightly coupled for the entire system to function effectively. By delivering increments and performing early user and system integration, we can identify issues and refine the design of these complex interactions at an early stage. \subsection{Justification of Proposing the Process Model}

The twelve modules of the SmartExam are not equally certain from day one. The security and user access components are quite standard and well-understood, while areas like face recognition, real-time websocket communication, or AI model for auto-grading feature more significant design risks and thus carry a higher potential for unforeseen challenges. A purely sequential development process would require freezing all these uncertainties upfront without concrete prototypes to validate them -- an impractical proposition for a year-long FYP project. The Agile model helps to mitigate this by allowing us to de-scope uncertainties, prototyping them at the earliest, integrating their results progressively and adjusting plans accordingly through ongoing review process. This also seamlessly aligns with our academic review milestones scheduled for mid-semester and end-of-semester; as we will be demonstrating functional increments each sprint, demonstrating progress to satisfy the review criteria will be an organic part of the development cycle.

\subsection{Steps of Process Model}

The project will be structured into eight Sprints, each spanning 4 weeks. All twelve modules will be incorporated within the sprint plan such that each Sprint yields a demonstrable, integrated set of functionalities for review.

\textbf{Sprint 1 (Weeks 1--4):} Requirement Analysis \& Planning phase. Includes collecting requirements from university IT and CS department stakeholders, detailed use-case modeling, formulating the product backlog, high-level architecture design, and getting supervisor's approval on the project scope.

\textbf{Sprint 2 (Weeks 5--8):} Authentication and Core Security components. Focus on delivering Module 1 (Device Binding and authentication) and Module 7 (User role and rights management). Functionalities include HWID capture (via WMI API calls), student login with HWID binding check, teacher and admin login mechanisms, and role-based access control for system views.

\textbf{Sprint 3 (Weeks 9--12):} Exam Creation \& Configuration modules. This sprint focuses on Module 8 (Exam creation and configuration) and Module 9 (Exam eligibility management and assignment control). It involves building the UI for defining exam parameters (title, description, time, etc.), question templates (coding and theory), test cases, app block/allow lists, and student eligibility logic.

\textbf{Sprint 4 (Weeks 13--16):} Delivers Module 2 (Pre-Exam Verification), Module 3 (Exam Dashboard), and Module 4 (Secure Exam Environment). The WPF client launched in fullscreen, blocking the Alt+Tab keys and Task Manager. Prior to session startup, hardware ready checks are conducted.

\textbf{Sprint 5 (Weeks 17--20):} Live Telemetry and Proctoring. Will deliver Module 5 (Live Monitoring Client Service) and Module 10 (Live Proctoring Dashboard). Background services are placed that log focus switches and process listings every couple of seconds. The data is streamed to a teacher dashboard (developed with React) via a SignalR WebSocket.

\textbf{Sprint 6 (Weeks 21--24):} Submission and AI Evaluation. Will deliver Module 6 (Submission and Backup) and Module 11 (AI-Assisted Evaluation). Teams will use autotoggle for submitting to locally encrypt and backup code on local devices, perform safe compilation of isolated code against test suites, and leverage an AI based on semantic similarity scoring for theory questions, providing a classwide plagiarism comparison matrix when submissions close.

\textbf{Sprint 7 (Weeks 25--28):} Reporting, Analytics and Auditing. Will deliver Module 12 (Logs, Analytics and Audit Trail). Team will develop immutable database tables for logging, the system performance Dashboard, and downloadable exam Reports using QuestPDF.

\textbf{Sprint 8 (Weeks 29--32):} Integration, Testing, and Final Refinement. Will deliver Module 1--12 (final code). Will deliver no new Modules. Will integrate and test all 12 modules into a single coherent application prototype. Will implement integration tests, bug fixes and write up and final academic Submission and Demonstration.
