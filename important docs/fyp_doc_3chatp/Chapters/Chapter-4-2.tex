\section{Functional Modeling}

The models below show how the backend stores and moves heartbeats, screenshots, answers, marks and audit records.

\subsection{Entity Relationship Diagram}

The data lives in Neon PostgreSQL and the schema is created by EF Core migrations from the models in \texttt{Backend\_API/Models}. We chose a relational database because marks, receipts and audit records need foreign keys and unique constraints \cite{er_diagram_lucidchart}. Every table except \texttt{ExamProctors} (composite key \texttt{ExamId}, \texttt{UserId}) has a GUID primary key. Figure~\ref{fig:erd_diagram} shows the schema in crow's-foot notation with each table's keys, a few key columns and the unique indexes.

The main relationships are:
\begin{itemize}[nosep]
    \item \textbf{One-to-one:} a user has at most one \texttt{DeviceBinding}; an answer has at most one \texttt{AiGradingResult} and one \texttt{TeacherGradeOverride}.
    \item \textbf{One-to-many:} an exam has many questions, a question many test cases, and a session many answers, monitoring events and screenshots.
    \item \textbf{Junctions:} \texttt{ExamAssignments} links a student to an exam and an optional workstation; \texttt{ExamProctors} links invigilators to exams; \texttt{PlagiarismResults} links two students on one question.
\end{itemize}

\subsection{Data Flow Diagram}

Processes are numbered (1.0--5.0), data stores are labelled D1--D8 after the tables they hold (D1 identity, D2 exams and questions, D3 Departments, Courses, Sections, SectionEnrollments, Labs, Workstations, AttendanceRecords, ExamAssignments, ExamProctors, D4 sessions and answers, D5 monitoring evidence, D6 grading results and reports, D7 Notifications, D8 AuditLogs) and arrows are data flows. The diagrams are drawn at three levels with the same numbering.

\subsubsection{DFD Level 0}

Figure~\ref{fig:dfd_level_0} shows the whole system as one process (the ASP.NET Core API) and its six external entities.

\begin{figure}[!htbp]
\centering
\includegraphics[width=0.85\linewidth]{Figures/dfd_level_0.png}
\caption{DFD Level 0: Context Diagram}
\label{fig:dfd_level_0}
\end{figure}

\begin{itemize}[nosep]
    \item \textbf{Student:} sends credentials, the hardware fingerprint, readiness results, heartbeats, screenshots and answers over REST; receives a JWT, exam questions and the submission receipt, and gets warnings, extra time and unlocks in the heartbeat reply.
    \item \textbf{Teacher and Invigilator:} the teacher sends exam settings, attendance and seat assignments; both send warnings, time extensions and force-submits for exams they supervise (the invigilator only for assigned exams) and receive live status over SignalR. The teacher also receives marks and PDF reports.
    \item \textbf{Admin/SuperAdmin:} sends user, role, lab and device-binding changes; receives audit logs and system analytics.
    \item \textbf{Email server (SMTP):} receives exam-scheduled, grades-released and announcement e-mails.
    \item \textbf{LLM grader (Groq or Gemini, optional, off by default):} receives theory answers with the model answer and rubric keywords, and code test results; returns a suggested mark or a code summary.
\end{itemize}

\subsubsection{DFD Level 1}

Figure~\ref{fig:dfd_level_1} splits the system into five processes; it is printed sideways so that its labels stay legible.

\begin{figure}[p]
\centering
\includegraphics[width=0.95\textheight,angle=90]{Figures/dfd_level_1.png}
\caption{DFD Level 1: Subsystem Overview}
\label{fig:dfd_level_1}
\end{figure}

\begin{sloppypar}
\begin{enumerate}[nosep]
    \item \textbf{1.0 Authenticate and bind device:} checks the password and hardware hash against \texttt{Users} and \texttt{DeviceBindings}, issues tokens and writes \texttt{AuditLogs}.
    \item \textbf{2.0 Configure exams and run sessions:} stores exams, questions, test cases, allowed apps, eligibility, seats and proctors, creates sessions and answers, and sends the exam rules to the client.
    \item \textbf{3.0 Lockdown and telemetry:} the client enforces the rules and sends heartbeats, event batches and screenshots. The server reads the assigned seat, the session and unread warnings, writes events and screenshots to D5, liveness to D4, \texttt{LastSeenAt} to D1 and \texttt{SEAT\_MISMATCH} to D8, and passes classed events and alerts to 4.0.
    \item \textbf{4.0 Live proctoring:} pushes status to teachers and invigilators over SignalR and stores their warnings in D7.
    \item \textbf{5.0 Evaluation and reporting:} grades submitted answers (calling the LLM only if enabled), compares submissions within the same exam, stores suggested marks and overrides, and builds PDF reports.
\end{enumerate}
\end{sloppypar}

\subsubsection{DFD Level 2}

Figure~\ref{fig:dfd_level_2} expands processes 3.0 (panel a) and 5.0 (panel b) with the same stores as level 1.

\begin{figure}[p]
\centering
\includegraphics[width=0.88\textheight,angle=90]{Figures/dfd_level_2.png}
\caption{DFD Level 2: Telemetry and Evaluation}
\label{fig:dfd_level_2}
\end{figure}

\begin{sloppypar}
\begin{enumerate}[nosep]
    \item \textbf{3.1--3.4 Telemetry:} \texttt{MonitoringController} receives heartbeats, event batches and screenshot uploads, checks the seat with \texttt{SeatGuard} and returns unread warnings in the reply (3.1). It records the heartbeat and process list, storing a heartbeat event only when something changed, and updates the session's \texttt{LastHeartbeatAt} and the device's \texttt{LastSeenAt}, so the heartbeat watchdog can mark a student disconnected (3.2). \texttt{ViolationClassifier} resolves each event's type and whether it is a violation; its severity (Warning/Suspicious/Violation) sets the live tile status (3.3). Events are saved, de-duplicated by \texttt{ClientEventId}, and violations are pushed as \texttt{ViolationEvent} (3.4).
    \item \textbf{5.1--5.5 Evaluation:} grading runs only when the exam has AI evaluation enabled; practice exams are not compared. The code runner tests answers against their test cases (5.1); MCQs are scored by key and theory answers by TF-IDF, or by the optional LLM (5.2); k-gram winnowing compares answers pairwise within the exam (5.3); marks, similarity pairs and overrides are saved (5.4); QuestPDF renders the report, and the audit log, analytics and student results are served (5.5).
\end{enumerate}
\end{sloppypar}
