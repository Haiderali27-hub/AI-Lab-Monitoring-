\section{Functional Modeling}

The models below show how SmartExam stores and moves heartbeats, screenshots, answers, marks and audit records.

\subsection{Entity Relationship Diagram}

The data lives in Neon PostgreSQL and the schema is created by Entity Framework (EF) Core migrations from the models in \texttt{Backend\_API/Models}. We chose a relational database because marks, receipts and audit records need foreign keys and unique constraints \cite{elmasri2016}. Every table except \texttt{ExamProctors} (composite key \texttt{ExamId}, \texttt{UserId}) has a GUID (uuid) primary key. \texttt{AuditLogs.ActorId} holds an id without a foreign-key constraint: each audit row's hash covers it, so it must keep the actor's id even after that user is deleted.

Figure~\ref{fig:erd_diagram} shows the entity relationship diagram in crow's-foot notation. It has 14 entities; each box lists the primary key (PK) above a line and the other columns below it, with their data types and the foreign keys (FK) marked. \texttt{Users} sits in the centre and is linked to \texttt{Roles}, \texttt{DeviceBindings}, \texttt{Exams}, \texttt{AuditLogs}, \texttt{ExamSessions} and \texttt{SeatingMaps}, while \texttt{Exams} owns the questions, allowed apps, sessions and seating maps, and each answer has one \texttt{AiGradingResults} row. The figure shows the main entities only. In the built schema the keys are GUIDs, not INT, the role is a column on \texttt{Users} instead of a \texttt{Roles} table, allowed apps are a JSON column on \texttt{Exams}, and the seat is stored on \texttt{ExamAssignments} with \texttt{Labs} and \texttt{Workstations} instead of \texttt{SeatingMaps}.

The main relationships are:
\begin{itemize}[nosep]
    \item \textbf{One-to-one:} a user has at most one \texttt{DeviceBinding}; an answer has at most one \texttt{AiGradingResult} and one \texttt{TeacherGradeOverride}.
    \item \textbf{One-to-many:} an exam has many questions, a question many test cases, and a session many answers, monitoring events and screenshots.
    \item \textbf{Junctions:} \texttt{ExamAssignments} links a student to an exam and an optional workstation; \texttt{ExamProctors} links invigilators to exams; \texttt{PlagiarismResults} links two students on one question.
\end{itemize}

\subsection{Data Flow Diagram}

The Data Flow Diagrams (DFDs) show how data moves between the users, the processes and the data stores. In the figures, a green rounded box is a process, a blue box with an icon is an external entity, an orange cylinder is a data store and a labelled arrow is a data flow. The system is the whole of SmartExam: the desktop client with its lockdown, the web panel and the API.

\subsubsection{DFD Level 0}

Figure~\ref{fig:dfd_level_0} shows SmartExam as one process, 0.0 SmartExam Platform, with four external entities around it: the Student User, the Teacher User, the System Administrator and the AI Grading Service. Each entity has one arrow into the process and one arrow out of it, so the student sends credentials, the HWID, telemetry and answers and receives the JWT token, questions and notifications. The teacher sends exam rules, seat maps and overrides and gets live alerts, PDF reports and grades, and the administrator sends configurations and unbinding approvals and gets audit logs and performance reports. In SmartExam the AI Grading Service is the optional LLM API for theory grading, which is off by default; the TF-IDF theory scores and the similarity scores are computed inside the API.

\subsubsection{DFD Level 1}

Figure~\ref{fig:dfd_level_1} splits the system into five processes: 1.0 Authenticate \& Bind Device, 2.0 Manage Exam Configuration, 3.0 Stream Telemetry \& Lockdown, 4.0 Monitor Live Proctoring \& Overrides and 5.0 Process Evaluation \& Reporting. The processes use the stores D1 Users \& Bindings, D2 Exams \& Whitelists, D4 Monitoring Events, D5 AI Grading \& Plagiarism and D6 Security Audit Logs, and the flows run from the sign-in at the top to grading and reporting at the bottom. Process 5.0 sends subjective answers to the AI Grading Service only when LLM grading is switched on, receives its scores, and returns final grades and PDF reports to the Teacher User.

\subsubsection{DFD Level 2}

Figure~\ref{fig:dfd_level_2} expands two processes of level 1. The upper box, 5.0 Evaluation \& Plagiarism Pipeline, reads D3 Exam \& Answers into 5.1 Run Isolated Compiler, 5.2 AI Semantic Grader and 5.3 Execute Plagiarism Checker, whose results meet in 5.4 Aggregate Grades; 5.4 writes the final grades to D5 and passes the data to 5.5 Render PDF Report for the Teacher User. The lower box, 3.0 Telemetry Streaming \& Analysis, takes the student's raw JSON packets through 3.1 Ingest Client Telemetry, 3.2 Validate Allowed Apps (with D2 Allowed Apps), 3.3 Analyze Anomalies and 3.4 Route Alerts \& Save Logs, which writes to D4 Monitoring Events and sends WebSocket warnings to the Teacher User. In the code, the plagiarism check (5.3) runs inside the API by k-gram winnowing and does not call the AI Grading Service, and the allowed-apps check (3.2) runs on the student's PC; the server then classifies the events it receives and passes violations to the live monitor through SignalR.
