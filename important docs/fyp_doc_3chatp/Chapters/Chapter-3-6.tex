\section{Project Risk Management}

Every software project carries risk. SmartExam carries specific ones: WebSocket reliability under concurrent load, WPF client lockdown effectiveness, HWID spoofing attempts, and module integration timing \cite{risk1}. Naming these risks early does not prevent them --- but it means the team already has a response ready when one materialises.

\subsection{Risk Identification}

Risk identification covers four categories for this project.

\textbf{Technical risks} include HWID spoofing via virtual machines (VirtualBox, VMware), WebSocket connection pool exhaustion during peak lab load, WPF fullscreen lockdown bypass via Task Manager shortcuts, and AI grading module returning inconsistent scores across Python versions \cite{pmc_cbt}.

\textbf{Schedule risks} include module integration taking longer than estimated in Sprint 8, documentation falling behind implementation by more than one sprint, and supervisor feedback arriving too late to revise a submitted chapter.

\textbf{Academic risks} include misalignment between what the SRS specifies and what the prototype actually delivers at the demonstration, and insufficient justification of design choices in the written report.

\textbf{Resource risks} include unavailability of physical lab workstations for testing, dependency on Neon PostgreSQL's free-tier connection limits, and team member unavailability during a critical sprint.

\subsection{Risk Analysis}

Not all risks deserve equal attention. A small chapter wording error is likely but low impact. A WebSocket failure during a live exam demonstration is moderately likely and high impact \cite{risk1}. The team evaluates each risk using a probability-impact scale and categorises the result.

\subsection{Risk Mitigation Plan}

Each risk in Table~\ref{tab:risk_matrix} has a prepared mitigation action.

\textbf{HWID spoofing:} The client queries three hardware identifiers simultaneously via WMI --- the BIOS serial number, motherboard manufacturer string, and physical disk ID. Virtualized environments cannot fake all three consistently. The server compares all three stored values, not just one, before authorising an exam session.

\textbf{Module integration delays:} Each module exposes a versioned REST API. Modules are developed and tested in isolation against a mock API contract. Integration only requires connecting live endpoints, not redesigning interfaces. This reduces Sprint 8 integration risk significantly.

\textbf{WebSocket overload:} The student WPF client buffers telemetry locally at 5-second intervals and uploads batched JSON packets rather than streaming continuous individual events. The API server uses a connection pool limited to 30 concurrent connections per lab session. This keeps database pressure predictable.

\textbf{Neon PostgreSQL limits:} The team monitors connection usage weekly during development. If the free-tier limit is approached, the application pool configuration is adjusted to enforce connection reuse before upgrading the plan.

\textbf{WebSocket reconnection failure:} If a student client loses its WebSocket connection mid-exam, it continues writing a local binary log file. When the connection restores, the client transmits the buffered delta immediately. No session data is lost during transient network interruptions.

\subsection{Risk Monitoring and Control}

Risk status is reviewed at every sprint boundary \cite{scrum1}. The team maintains a shared risk register tracking each item's current likelihood (updated as more is known), whether a trigger condition has fired, and whether the mitigation action was effective. If a risk escalates --- for example, if integration testing reveals that two modules share an incompatible data schema --- the team elevates it to a sprint blocker and adjusts the timeline before continuing.

This is not passive calendar watching. It is active risk state management. A risk that changes from Low to Medium between sprints gets a mitigation plan before it reaches High.
