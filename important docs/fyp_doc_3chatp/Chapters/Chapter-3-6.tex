\section{Project Risk Management}

Risk management is the process through which potential problems are identified, assessed, and prepared for before they seriously affect project success \cite{risk1}. In the proposed AI-Driven Lab Exam Monitoring and Management System, risk management is especially important because the project involves technical integration, real-time workflow assumptions, multiple stakeholder expectations, and strict academic deadlines. Risks do not need to become actual failures if they are recognized early and managed in a disciplined way.

\subsection{Risk Identification}

Risk identification involves systematically documenting potential threats to the project’s technical stability, schedule viability, and operational success. By categorizing these risks, the development team can define clear boundaries and establish individual focus areas for mitigation. The identified risks for this project are divided into four primary categories:

\subsubsection{Technical and Security Risks}
Technical risks represent threats arising from software limitations, hardware failures, or security vulnerabilities during exam execution. A primary concern is workstation Hardware ID (HWID) spoofing or virtual machine (VM) evasion, where a student attempts to bypass the lock-down client by running it inside a guest operating system, leaving the host operating system free for unauthorized external search or communication. Other technical risks include WebSocket connection latency under high concurrency (e.g., when 40+ terminals stream screenshot packets simultaneously), low-level Windows API hook failures on different OS updates, and potential memory leaks in the WPF client background threads.

\subsubsection{Schedule and Integration Risks}
Schedule risks include the possibility of missing critical development milestones due to complexity or dependency conflicts. For this system, the integration of different component layers—such as connecting the Kestrel REST API with the Docker grading host and the React proctoring dashboard—represents a significant integration risk. Delays in completing foundational modules, such as user authentication or exam configuration pipelines, would directly delay subsequent modules like live proctoring or QuestPDF reporting. Additionally, the academic report documentation falling behind implementation is a persistent schedule risk.

\subsubsection{Resource and Environmental Risks}
Resource risks arise from constraints on physical facilities, equipment, or team availability. The primary resource risk is the temporary unavailability of the physical university computer labs for live testing and scenario-based validation. Hardware malfunctions or local network latency spikes in the university lab could also disrupt testing. Furthermore, individual team member illness, academic workload overload, or unexpected unavailability during a critical sprint represents a significant resource threat to project continuity.

\subsubsection{Data Privacy and Accreditation Risks}
Data privacy risks involve the accidental exposure of sensitive student records, active exam questions, or monitoring telemetry (such as webcam snapshots and desktop focus logs). If unauthorized users gain access to the database or storage servers, it could lead to institutional policy violations and compromise the integrity of the examination. Furthermore, failing to align the system’s modules with standard academic policies and department requirements could result in a lack of accreditation or approval by evaluators.

\subsection{Risk Analysis}

Risk analysis helps the team determine which risks deserve the most attention. A risk is not important only because it is possible; it becomes important when its likelihood combines with meaningful impact. For example, a small wording correction in a chapter may be likely but low impact, whereas instability in a monitoring feature during late-stage integration may be both moderately likely and highly disruptive. The team therefore evaluates risks in terms of both probability and seriousness.

To make this evaluation systematic, the system uses a semi-quantitative risk rating model. Each risk is evaluated on two parameters: Likelihood (L) and Impact (I). Both parameters are assigned a numerical score on a scale of 1 to 3:
\begin{itemize}
    \item \textbf{Likelihood (L):} Low = 1, Medium = 2, High = 3 (Very Low is treated as 1 for scoring purposes).
    \item \textbf{Impact (I):} Low = 1, Medium = 2, High = 3.
\end{itemize}

Using these scores, the Risk Priority Score (RPS) is calculated using the following formula:
\begin{equation}
    \text{RPS} = \text{Likelihood (L)} \times \text{Impact (I)}
\end{equation}

Based on the calculated Risk Priority Score, the overall Priority is determined according to these thresholds:
\begin{itemize}
    \item \textbf{Low Priority (RPS 1--2):} Minor risks that do not disrupt development or execution. Mitigated with standard checks.
    \item \textbf{Medium Priority (RPS 3--4):} Moderate risks that require active monitoring and secondary planning.
    \item \textbf{High Priority (RPS 6--9):} Critical risks that can cause project failure or security breaches. Requiring active, primary mitigation strategies.
\end{itemize}

\subsection{Risk Mitigation Plan}

Risk mitigation involves planning responses before problems grow. For each of the priority areas defined in the risk rating matrix, the project team has established concrete mitigation protocols to minimize their likelihood and impact:

\subsubsection{Mitigation for Technical and Security Threats}
To mitigate workstation HWID spoofing and virtual machine evasion, the WPF student client integrates hypervisor detection checks. These checks query local WMI classes for virtual disk names, BIOS serial indicators, and hypervisor registry keys, blocking exam access if a guest OS environment is detected. To handle WebSocket latency and system overload, SignalR hubs utilize asynchronous database calls, local client-side buffering of logs during temporary dropouts, and optimized screenshot compression to reduce network bandwidth. Data privacy is maintained by storing all monitoring media in private bucket storage, encrypting passwords with BCrypt, and using JWT tokens to enforce role-based access.

\subsubsection{Mitigation for Schedule and Integration Threats}
To prevent late-stage integration failures, the development team uses modular interfaces with strict API contracts. This separation of concerns allows components (such as the Docker sandbox compiler and React web panel) to be developed and tested independently before full integration. Weekly sprint reviews and progress tracking against the WBS ensure that delay anomalies are identified early, allowing resources to be reallocated. Documentation is kept synchronized by writing and updating chapter drafts alongside each corresponding module's completion.

\subsubsection{Mitigation for Resource and Environmental Threats}
To mitigate laboratory unavailability, the team implements local workstation simulators and test harnesses. This allows end-to-end testing of lockdown features, WebSocket transmission, and auto-grading compilation on local laptops before deploying them to the physical lab environment. To handle team member unavailability, all source code is synchronized on shared repository branches, and task definitions are documented in detail, ensuring that another team member can cover critical assignments if needed.

\subsection{Risk Monitoring and Control}

Risk management is not a one-time exercise performed only at the proposal stage. Risks must be monitored throughout the semester as the project evolves. New risks may appear when modules become more detailed or when feedback changes priorities. Therefore, the team should review risk status regularly, especially after each sprint or milestone.

Continuous risk monitoring is integrated into the Agile cycle. During weekly team meetings, the status of active threats is evaluated against critical development dependencies, and the risk rating matrix is adjusted as progress is made. For instance, once the Docker compiling sandbox is successfully integrated and tested, its risk rating is downgraded. This active tracking ensures stable execution, maintains project schedule control, and reduces the likelihood that late-stage integration issues will disrupt final prototype delivery.
