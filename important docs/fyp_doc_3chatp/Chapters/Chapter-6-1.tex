\chapter{SYSTEM INTERFACE AND PHYSICAL DESIGN}
\label{chap:system_interface_physical_design}

This chapter shows what each user sees and how the data is stored. Section~\ref{sec:system_user_interfaces} follows an exam from start to finish: the student's desktop client, exam set-up, live invigilation, evaluation, administration and the student portal. Section~\ref{sec:physical_tables} lists the 29 database tables and the columns of the six core ones.

\section{System User Interfaces}
\label{sec:system_user_interfaces}
SmartExam has two front ends: a WPF desktop client (.NET~9) in which students sit the exam, and a React web panel with one route group per role (\texttt{/admin}, \texttt{/teacher}, \texttt{/invigilator}, \texttt{/student}). Both follow common usability heuristics: the system status is always visible (connection, last save, tile status), final actions such as submit and force-submit ask for confirmation, and controls look the same across roles \cite{nielsen_heuristics}. The web figures are captured from the running panel by a Playwright script (\texttt{Admin\_Web\_Panel/tests/docs}) against the in-memory backend with the seeded demo data; a scripted client plays the desktop app and uploads the screen captures. The desktop figures are rendered off-screen from the client's own XAML (Extensible Application Markup Language) views with values from the same run, because the lockdown window cannot be captured safely on a development PC. The student, invigilation and evaluation figures show one exam, the Mid-Term Lab Exam (Demo), in Enforce mode with a required system check and webcam.

The client reads the BIOS, system-disk and baseboard serials; the server hashes them with SHA-256 into the hardware ID (HWID) and keeps only the hash in \texttt{DeviceBindings}, so a login from another PC is refused (FR1).

\subsection{Users}
Administrators are \texttt{Users} rows with role Admin or SuperAdmin, so there is no separate admin table; only a SuperAdmin may manage Admin and SuperAdmin accounts (FR7). \texttt{Email} and \texttt{RollNumber} have unique indexes, the latter filtered on \texttt{IS NOT NULL} (Table~\ref{tab:users_table}) \cite{efcore_indexes}. Passwords are salted PBKDF2-HMAC-SHA256 hashes \cite{rfc8018} at 600{,}000 iterations, as OWASP recommends \cite{owasp_pwd}; the iteration count is stored with each hash, so older hashes are re-hashed at the next successful login \cite{nist80063b}. A student's PC is kept in \texttt{DeviceBindings} (one row per student, deleted with the user).

\subsection{AuditLogs}
Table~\ref{tab:auditlogs_table} lists the columns. Each row's \texttt{Hash} is the SHA-256 of its own fields and of the previous row's hash (\texttt{PrevHash}; 64 zeros for the first row), so editing a row, or deleting one that later rows follow, makes verification fail, which the badge in Figure~\ref{fig:ui_audit_logs} reports. \texttt{ActorId} is an indexed plain id rather than an FK, so a deleted user's rows keep the id their hash covers. The three chain columns are null only for rows written before the chain was added, until an administrator seals them with the backfill.
