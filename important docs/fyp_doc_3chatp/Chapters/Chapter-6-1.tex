\chapter{SYSTEM INTERFACE AND PHYSICAL DESIGN}
\label{chap:system_interface_physical_design}

In the software development lifecycle, the system interface and physical design phase translates the static logical structures and dynamic workflows into physical components that are directly usable by human actors and compile-ready for database servers. While use cases and sequence diagrams detail functional boundaries and message routing paths, this chapter focuses on the design of the user interfaces (UI) and the physical database layout. The user interface design establishes the visual viewport, navigational controls, input fields, and feedback mechanisms that shape the user experience (UX) for students and teachers. Simultaneously, the physical database design defines the concrete SQL schemas, column types, lengths, constraints, and relational indexes required to store and query telemetry data, exam configurations, and grading results securely and efficiently. By mapping both the interactive front-end layouts and the persistent back-end storage schemas, the physical design guarantees that the software prototype remains secure, performant, and resilient under real-world lab conditions.

\section{System User Interfaces}
A system user interface (UI) represents the graphical and interactive gateway through which human users interact with software systems. The UI establishes how buttons, text forms, selection toggles, tables, and charts are arranged, ensuring that users can execute tasks efficiently without cognitive overload. In the SmartExam platform, the UI design is divided into two distinct clients: a native Windows WPF desktop client for student exam execution and a responsive React web dashboard for instructor supervision and evaluation. The design prioritizes visual clarity, clean layouts, and responsive components, adhering to modern UI/UX guidelines such as accessibility, clear warnings, and real-time state updates. By maintaining consistency in color palettes, typography, and controls, the platform minimizes usability errors during exams and supports seamless coordination between invigilators and candidates.

The interfaces detailed below cover the user views of the completed platform modules, displaying the operational layouts for candidate authentication, device binding, diagnostics checks, secure workspace lockdown, proctoring dashboards, live telemetry monitors, and compiler results.

\subsection{Student Login and Device Binding Interface}
The student login and device binding interface is the initial entry screen of the WPF desktop client, designed to authenticate candidates and enforce device-locking policies. The layout consists of input fields for the student's institutional email and password, alongside a status card indicating the system's connection state. When the candidate clicks the login button, the client runs local Windows APIs to retrieve motherboard, CPU, and network MAC addresses, hashing these details to form a unique Hardware ID (HWID) payload. This interface handles first-time registration by binding the incoming HWID hash to the student's profile in the database. On subsequent login attempts, it validates that the workstation's hardware details match the registered binding, displaying a validation warning if a discrepancy is detected. \subsection{Pre-Exam Workstation Diagnostics Interface}
The pre-exam diagnostics interface provides students with a visual check of their workstation's readiness before an assessment begins. The screen renders a list of automated tests, including webcam connectivity, microphone checks, network latency, and running background processes. Each diagnostic task features a progress loader that transitions into a green success mark or a red error alert based on the verification outcome. If the diagnostics detect a disabled camera, a blocked background process (such as a communication app or a screen sharing program), or a weak connection, the client blocks access to the exam workspace and prompts the student to resolve the issue. By providing a clear checklist, this interface ensures that all technical requirements are met before the exam timer begins. The interface layout is shown in Figure~\ref{fig:ui_student_diagnostics}.

\subsection{Student Exam Lockdown Workspace}
The student exam lockdown workspace is the central viewport where candidates view and complete their assessments. Once diagnostics pass, the client enters a secure fullscreen lockdown mode, blocking task-switching keystrokes (such as Alt+Tab or the Windows key) and disabling access to the Task Manager. The workspace layout divides the screen into three main sections: a left-hand navigation pane showing question indices, a central question card presenting instructions and inputs, and a top bar displaying the remaining time and autosave status. The central input panel adapts to the question type, rendering a rich-text editor for theoretical answers or a code editor with syntax highlighting for practical tasks. A persistent connection status indicator ensures that the student is aware of their connection to the telemetry hub. The exam workspace interface is shown in Figure~\ref{fig:ui_student_workspace}.

\subsection{Device Bindings and Hardware Identifier Interface}
The device bindings and hardware identifier interface gives administrators full control over physical machine locks. The dashboard lists all user accounts alongside their bound CPU and motherboard HWID hashes, the time the binding was established, and the workstation details. If a student needs to switch workstations due to a verified hardware failure during exam day, the instructor can use this interface to approve a "device unbinding request". Clicking the unbind button releases the existing HWID record in the database, allowing the candidate to log in and lock a new workstation on their next attempt. \section{Physical Database Tables}
Physical database design translates the logical Entity Relationship Diagram (ERD) into actual relational SQL tables implemented on the Neon PostgreSQL platform. This stage involves defining table columns, data types (e.g., \texttt{SERIAL}, \texttt{VARCHAR}, \texttt{TIMESTAMP}), lengths, nullable/non-nullable constraints, primary key bounds, and foreign key relations. Proper physical design ensures data integrity, prevents redundant records, and supports quick data retrieval. In the SmartExam database, columns that are frequently filtered or joined are indexed, and foreign keys are configured with explicit cascading actions to maintain consistency across tables. 

Below are the physical schema table specifications for the five core entities of the SmartExam system, structured using the required double-hline format.

\subsection{Users Table (Users)}
The \texttt{Users} table is the central store for candidate, instructor, and administrator credentials within the relational database. It manages account profiles, storing encrypted password hashes and role associations. The table uses a unique index on the email column to accelerate authentication queries, and enforces referential integrity through a foreign key link to the Roles table. This structure prevents unauthorized access and forms the basis for session authorization. The physical database schema for the users table is defined in Table~\ref{tab:users_table}.

\subsection{Device Bindings Table (DeviceBindings)}
The \texttt{DeviceBindings} table binds student user accounts to their physical workstations. By mapping a student's database ID to a unique motherboard and CPU hardware hash (HWID), this table prevents proxy exam attempts. It enforces a strict one-to-one relationship via a unique constraint on the user identifier, ensuring a student cannot register multiple devices.
