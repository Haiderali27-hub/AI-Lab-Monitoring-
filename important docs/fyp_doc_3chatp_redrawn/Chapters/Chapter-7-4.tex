\subsection{System Test Case}\label{subsec:system_tests}

The system test case runs one complete exam across the web panel, the backend and the student client, from the first account to the last audit check. It is executed in the Playwright \texttt{chromium} project, where the web panel runs in headless Chromium and the desktop-client simulator sends the HTTP calls of the WPF client in the same test, so one action can be followed from the student PC to the teacher's screen and back. All 113 tests of that project passed.

\subsubsection{System Test Case: Complete Exam from Set-up to Audit}\label{subsubsec:stc_1}
This case covers all twelve modules and the five roles in the order of a real exam day.

\paragraph{Test Method}
{\sloppy Black-box end-to-end testing through the user interface. Each stage of the scenario is a separate Playwright test that creates its own students and exam, so the scenario is run as a chain of tests rather than as one long test; a stage may combine several catalogue tests of the same flow. The browser suite uses the seeded lab seats (R1C1, R1C2), so lab creation (step~3) is checked by an xUnit test against the in-memory host. The steps on the real WPF client cannot be driven by the browser and are on the lab checklist.\par}

\paragraph{Test Case Description}
{\sloppy \textbf{Precondition:} the Playwright seed accounts (\texttt{admin@\allowbreak{}smartexam.\allowbreak{}com}, \texttt{teacher@\allowbreak{}smartexam.\allowbreak{}com}, \texttt{root@\allowbreak{}smartexam.\allowbreak{}com}, \texttt{invigilator@\allowbreak{}smartexam.\allowbreak{}com}) and the seeded lab seats. \textbf{Description:} the admin creates users and labs, the teacher creates the exam and decides eligibility, the student signs in on the bound PC and sits the exam, the invigilator monitors and warns, and the exam is submitted, graded, exported and checked in the audit log. \textbf{Pass:} every stage shows the expected screen or reply. \textbf{Fail:} any stage shows another result or an error.\par}

Result: Pass for every automated stage; the lab stage is pending.

Six (D-07, D-16, D-19, D-20, D-22, D-26) were found by code review and one (D-48) while implementing Module~12; two (D-33, D-49) were timing-sensitive tests rather than product defects. Most serious defects were access-control faults that appear only when two users of the same role meet, or failure paths of the desktop client (crash, network loss, camera error) found by unit tests with fakes. In summary, SmartExam was tested at three levels with 921 automated tests, of which 920 passed, none failed and one was skipped (SEC-A-01, covered by SEC-I-04), and every test case marked Pass in this chapter is backed by a passing test from that run. The 49 recorded defects are all fixed; those found by a test are kept as regression tests. The checks that need a real lab PC and the load test are still pending and are reported as such.
