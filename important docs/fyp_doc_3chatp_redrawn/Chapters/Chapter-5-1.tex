SmartExam has three parts: the WPF \texttt{Student\_Desktop\_App} on the lab workstations, the React \texttt{Admin\_Web\_Panel} for staff and students, and the ASP.NET Core \texttt{Backend\_API}, which keeps its data in PostgreSQL. \section{Structure Diagrams}
\label{sec:structure_diagrams}
Structure diagrams show the static parts of a system: its classes, components and machines \cite[Annex~A]{omg_uml251}. Agreeing on them early let us build the client, panel and API in parallel.

\subsection{Class Diagram}
\begin{sloppypar}
A class diagram shows classes, their attributes and their associations \cite{class_diagram_uml, class_diagram_sparx}. The design is drawn in four parts; the three larger parts each take two figures, (a) and (b). Figure~\ref{fig:class_diagram} shows the core entities, which are Entity Framework Core classes in \texttt{Backend\_API/Models} (key entities only; the full 29-table schema is the ERD in Figures~\ref{fig:erd_diagram} and~\ref{fig:erd_diagram_b}). These entities hold data only: their operations belong to the client, service and controller classes of Figures~\ref{fig:class_diagram_client} to~\ref{fig:class_diagram_server2_b}, and roles are values of the \texttt{UserRole} enumeration, not subclasses of \texttt{User}. Each student has at most one \texttt{DeviceBinding}, which ties the account to one workstation. A teacher owns exams through the sections they teach, and \texttt{ExamProctor} links invigilators to exams; these two links give the \texttt{Owner} and \texttt{Proctor} access levels of \texttt{ExamAccessService}. \texttt{AuditLog} has no association: its \texttt{ActorId} is covered by the row hash and is not a foreign key.
\end{sloppypar}

\begin{sloppypar}
In Figure~\ref{fig:class_diagram} each box is one entity with its key attributes and their types. A plain line is an association with its multiplicity (1, 0..1 or *) at each end, and a line with a filled diamond means the part belongs to the whole: an exam owns its questions, and a session owns its answers and monitoring events. The key point is that \texttt{ExamSession} links one student to one exam, and everything recorded during the exam (answers, monitoring events and, through the answers, grading results) hangs off that session.
\end{sloppypar}

\subsection{Deployment Diagram}
\begin{sloppypar}
A deployment diagram maps software artefacts onto nodes and communication paths \cite[Cl.~19]{omg_uml251}, \cite{deployment_diagram_vp}. Figure~\ref{fig:deployment_diagram} shows lab workstations running the WPF client with its Open Neural Network Exchange (ONNX) models, encrypted outbox and webcam; browsers running the React panel, whose static build comes from a web host; and an application server whose ASP.NET Core~9 environment runs the API, its SignalR hub (\url{/hubs/monitoring}) and the hosted background services, beside a Docker \texttt{gcc:13} container and a MinGW fallback. The server connects to Neon PostgreSQL, an SMTP server and, optionally, an LLM API. The client and the web panel call the API over REST, using plain HTTP on the shipped localhost configuration and HTTPS behind a Transport Layer Security (TLS) endpoint in a lab deployment; the API itself does not enforce HTTPS. Only the panel adds a SignalR connection, for live updates.
\end{sloppypar}

\begin{sloppypar}
In the figure each 3-D box is a node (a machine or a run-time environment), each item inside it is an artefact deployed there, and each arrow is a communication path labelled with its protocol. The desktop artefact is \texttt{Student\_Desktop\_App.exe}; its ONNX models run through OpenCvSharp4, and its outbox and answer backup are encrypted with AES-256-GCM under a key wrapped by DPAPI. The web host is the Vite development server on port 5173, or any static server, which serves the \texttt{dist/} build of \texttt{Admin\_Web\_Panel} over HTTP. On the application server Kestrel listens on port 5050 (set with \texttt{--urls}) and serves REST under \url{/api/*} and SignalR at \url{/hubs/monitoring}. The \texttt{gcc:13} container runs with \texttt{--network none} and a read-only file system, while the MinGW \texttt{g++} fallback is not isolated. The server keeps captures in an \texttt{Evidence/} folder and PDF, Excel and ZIP files in \texttt{Reports/}. It reaches Neon PostgreSQL (database \texttt{neondb}, 29 tables) through Npgsql and EF Core with \texttt{SSL Mode=Require}, the SMTP server \texttt{smtp.gmail.com} on port 587 through MailKit with STARTTLS, and the optional LLM API (Groq or Gemini, off by default) over HTTPS. The client sends heartbeats every 10 seconds, event batches, captures and answers over REST with a JWT, and only the panel opens a SignalR WebSocket. The key point is that only the API server touches the database, the files and the code runners.
\end{sloppypar}

\begin{sloppypar}

Submission triggers grading and plagiarism detection, and the Grading controller also calls the grading services directly.
\end{sloppypar}

\begin{sloppypar}
Each box in the figure is a component, a package groups the components of one part, and a small circle with a socket is an interface that one side provides and the other requires. In the desktop client, the windows and view models are \texttt{LoginWindow}, \texttt{ExamDashboard} and \texttt{ExamWindow}; the readiness checks are \texttt{ReadinessCheckService} with \texttt{ReadinessPolicy}; lockdown is \texttt{LockdownCoordinator} with \texttt{KeyboardHookService}, \texttt{ProcessGuardService}, \texttt{ClipboardGuardService}, \texttt{DeviceGuardService} and \texttt{TaskManagerRegistryGuard}; live monitoring is \texttt{LiveMonitoringService} with \texttt{MonitoringSpool}, \texttt{EventBatcher} and \texttt{WarningInbox}; capture and webcam vision are \texttt{EvidenceCaptureService}, \texttt{WebcamMonitorService} and \texttt{WebcamVision} (YuNet, YOLOX-Nano); and \texttt{ApiClient} works with \texttt{TokenRefreshGate}. The 16 controllers are Auth, Users, Labs, Departments, Courses, Attendance, Exams, Monitoring, MonitoringEvidence, Incidents, Grading, Analytics, Audit, Notifications, StudentPortal and AdminMaintenance. \texttt{MonitoringHub} offers \texttt{JoinExamGroup}, \texttt{SendWarning}, \texttt{ForceSubmitSessionById}, \texttt{ExtendStudentTime}, \texttt{UnlockSession} and \texttt{RelockSession}.
\end{sloppypar}

\begin{sloppypar}
The domain services are \texttt{SubmissionService}, \texttt{ExamAccessService}, \texttt{SeatGuard}, \texttt{AuditService}, \texttt{AuditChain}, \texttt{RefreshTokenService}, \texttt{ViolationClassifier}, \texttt{EligibilityCalculator}, \texttt{NotificationService}, \texttt{EmailService}, \texttt{AnalyticsService}, \texttt{ReportExportService} and \texttt{EvidenceStorage}. The key point is that both front ends meet the server only at the two interfaces, REST and the hub.
\end{sloppypar}

\section{Behavioural Diagrams}

Behavioural diagrams show run-time behaviour: steps, messages and state changes \cite[Annex~A]{omg_uml251}.

\subsection{Activity Diagrams}
\begin{sloppypar}
An activity diagram shows a workflow with its decisions and parallel branches \cite[Cl.~15]{omg_uml251}, \cite{activity_diagram_vp}. Figure~\ref{fig:activity_diagram} gives the whole student flow in Student, Desktop App, Server and Teacher swimlanes: login with the device check, readiness checks, the start gate, answering with lockdown and monitoring in parallel, then the end of the session by submit, timer, force-submit or timeout, followed by grading and teacher review. Each column is one swimlane, a diamond is a decision with its answers in brackets, and the two thick bars open and close the part where answering and monitoring run at the same time.
\end{sloppypar}

\begin{sloppypar}
The steps map to these calls. Login is \texttt{POST} \url{/api/auth/student-login} with the v2 fingerprint, built from the BIOS, disk and baseboard serials; a refusal is 401 \texttt{UNAUTHORIZED}, \texttt{FORBIDDEN} or \texttt{DEVICE\_MISMATCH}, and a good login returns a JWT and a refresh token. The seven readiness checks are Network, ClockSkew, ScreenCapture, Camera, Microphone, SecureMode and Disk; their results go to \texttt{POST} \url{/api/exams/{id}/readiness}, and a failed check blocks only if the exam requires it. Check-in sends an Attendance event to \texttt{POST} \url{/api/monitoring/event}. The start is \texttt{POST} \url{/api/exams/student/start}; its refusals include \texttt{NOT\_ELIGIBLE}, \texttt{SEAT\_MISMATCH}, \texttt{EXAM\_NOT\_STARTED} and \texttt{READINESS\_REQUIRED}, and a yes creates an InProgress \texttt{ExamSession} or resumes one. During the exam the heartbeat goes out every 10 seconds, and ``webcam AI'' means YuNet and YOLOX-Nano. \texttt{FinalizeAsync} locks the session with a SHA-256 receipt; when AI evaluation is on it grades MCQ and theory (TF-IDF) answers and queues code, and winnowing runs only for non-practice exams. \texttt{GradingWorker} later runs the queued code tests in Docker \texttt{gcc:13} or the MinGW fallback. The client verifies the receipt after a submit or an automatic submit, and shows Exam Ended after a force-submit or a timeout. The teacher's last step uses the \url{grading/accept-ai} and \url{answers/{id}/override} routes.
\end{sloppypar}

\subsubsection{Login and Pre-Exam Checks (M1, M2; UC-01, UC-02)}
\begin{sloppypar}
In Figure~\ref{fig:activity_auth} the client sends the email or roll number, the password and a hardware fingerprint to \url{/api/auth/student-login}, which accepts 10 requests a minute per IP address and then returns 429 Too Many Requests. The v2 fingerprint joins the BIOS, system-disk and baseboard serials read through WMI, and the legacy v1 fingerprint is sent with it; the server stores only the SHA-256 hash. Wrong credentials return 401 \texttt{UNAUTHORIZED} (\texttt{LOGIN\_FAILED}). A non-student account gets 401 \texttt{FORBIDDEN} and a missing HWID gets 400 \texttt{BAD\_REQUEST}, both without an audit entry. The first login saves the hash as the student's \texttt{DeviceBinding} (\texttt{DEVICE\_BOUND}), an old v1 binding is upgraded when the legacy fingerprint matches (\texttt{DEVICE\_REBOUND}), and a login from another machine is refused with \texttt{DEVICE\_MISMATCH}.
\end{sloppypar}

\begin{sloppypar}
The server's checks in the figure run from top to bottom, and the first ``no'' ends the login with a refusal, so a password is never checked for a caller that is over the rate limit. A successful login updates \texttt{LastSeenAt}, re-hashes a password stored with an older PBKDF2 setting, creates a \texttt{UserSession}, is audited as \texttt{LOGIN\_SUCCESS} and returns a JWT and a refresh token. The client keeps the tokens in \texttt{SessionStore}, renews them through \url{/api/auth/refresh}, and opens the dashboard.
\end{sloppypar}

\begin{sloppypar}
Figure~\ref{fig:activity_diagnostics} shows the seven checks in \texttt{ReadinessPolicy}. The client first loads the exam's requirements with \texttt{GET} \url{/api/exams/student/current}. Network passes when the best round trip is 2 seconds or less, ClockSkew when the clock is within 60 seconds of the server, ScreenCapture when the screen can be captured, and Disk when at least 200~MB is free. Camera needs a frame that is not dark with exactly one face (found by YuNet), and Microphone needs a device; these two run only when the exam requires them. SecureMode needs one monitor if \texttt{BlockMultiMonitor} is set, no remote session, no virtual machine and a working keyboard hook, and it is skipped when lockdown is Off.
\end{sloppypar}

\begin{sloppypar}
The figure is a loop: the client runs the checks, the server records the result, and the loop repeats until every required check passes. Retry re-runs only the failed item, but all results are sent again to \texttt{POST} \url{/api/exams/{id}/readiness}, where \texttt{ExamsController} recomputes \texttt{passedAll}, saves a \texttt{ReadinessCheck}, audits \texttt{READINESS\_PASSED} or \texttt{READINESS\_FAILED} and pushes \texttt{ReadinessUpdated}. Check In sends an Attendance event. Start opens at \texttt{StartTime} minus \texttt{EarlyJoinMinutes} if the student is eligible and on the right seat, and a pass is valid for 30 minutes: after that, \texttt{student/start} returns \texttt{READINESS\_REQUIRED}.
\end{sloppypar}

\subsubsection{Practice Exam and Exam Workspace (M2, M4, M5; UC-03, UC-06, UC-07)}
\begin{sloppypar}
Practice exams (\texttt{Exam.IsMock}) are listed by \texttt{GET} \url{/api/exams/student/practice} and started with \texttt{POST} \url{/api/exams/{id}/start-session} instead of the real exam's \url{/api/exams/student/start}. They run in the same exam window, in Report mode, where apps are only reported, and without the webcam, so students meet the editor and lockdown beforehand (Figure~\ref{fig:activity_readiness}). The server checks eligibility, the open time, the seat and readiness first; a refusal is a 400 or 403 with \texttt{EXAM\_NOT\_STARTED}, \texttt{SEAT\_MISMATCH} or \texttt{READINESS\_REQUIRED}, shown in a message box. Answers use the same save-answer and submit endpoints as a real exam. Practice exams do not count towards results: they are auto-marked when AI evaluation is on, but never checked for plagiarism and left out of the student's results and analytics. The receipt shows no mark, and after it is shown the attempt count goes up by one.
\end{sloppypar}

\subsubsection{Autosave, Recovery and Submission (M6; UC-08)}
\begin{sloppypar}
An answer is saved 10 seconds after its first unsaved edit, on question change and on focus loss, by \texttt{POST} \texttt{save-answer}. Each edit raises the answer's \texttt{Revision} by one, and within a second it also goes to a local \texttt{.seb} backup encrypted with AES-256 in Galois/Counter Mode (AES-256-GCM), whose key is protected by the Windows Data Protection API (DPAPI). The server keeps the newer revision and answers 200 OK or 409 \texttt{STALE\_REVISION}. Failed saves wait in \texttt{OfflineSaveQueue}, which keeps the newest revision and replays the saves in order when the network returns.
\end{sloppypar}

\begin{sloppypar}
Figure~\ref{fig:activity_recovery} has two parts: the upper loop is the normal save cycle, and the lower part is what happens after a crash. A normal close means the exam was submitted or ended by the server (see the submission flow below). If a crash or power cut closed the exam, the student relaunches the app and logs in; \texttt{student/start} returns the same InProgress session, and the client reads the server's answers with \texttt{GET} \url{/api/exams/sessions/{sid}/answers}. ``Backup intact'' means the backup passes the AES-GCM tag check. In that case it is merged with the server copy, the higher revision winning, and anything the server lacks is replayed; a failed check uses only the server copy and is reported as \texttt{BackupTampered}.
\end{sloppypar}

\subsubsection{Grading, Reports and Audit (M11, M12; UC-16 to UC-18, UC-21)}
\begin{sloppypar}
After submission (Figure~\ref{fig:activity_grading}) \texttt{FinalizeAsync} sets the session to Submitted, ForceSubmitted or TimedOut with a SHA-256 receipt. MCQ answers are checked against the key at once. Theory answers are scored at once by TF-IDF \cite{salton1988} (0.7 times the cosine similarity plus 0.3 times the key-term coverage) only when the LLM grader is off; otherwise they are queued for it. A blank coding answer gets 0 with High confidence, and with \texttt{Runner = None} code is not run (0, Low) while \texttt{CodeAnalyzer} still runs. Queued coding answers also get pending test-case rows. Plagiarism is checked pairwise with $k$-gram winnowing \cite{winnowing} ($k = 5$ tokens, window $w = 4$, so any shared run of 8 tokens is found) for non-practice exams, and pairs at or above the threshold are kept.
\end{sloppypar}

\begin{sloppypar}
The left branch of the fork is the background work. \texttt{GradingWorker} runs two consumers and hands each queued coding answer to \texttt{GradingService}, which runs it against its test cases \cite{alamutka2005} in Docker \texttt{gcc:13} (no network, with memory, CPU and time limits) or in the MinGW \texttt{g++} fallback (not isolated). A run is tried up to 3 times before it is marked Failed (0, Low); a compile error gives 0 with High confidence and the compiler output; otherwise \texttt{OutputComparer} and \texttt{TestCaseScorer} score the cases, and \texttt{CodeAnalyzer} checks loops, recursion and hard-coding. The result is saved as \texttt{AiGradingResult} and \texttt{TestCaseResults}, audited as \texttt{AI\_GRADING\_COMPLETED} (or \texttt{AI\_GRADING\_FAILED}) and pushed as \texttt{GradingCompleted}. In the right branch the teacher reviews marks, test cases and a plagiarism heat map. Accept-all (\texttt{accept-ai}) takes only Graded rows with a real suggestion, leaves Pending and Failed rows as not ready, needs a manual mark for not-run or compile-only rows, and is audited as \texttt{AI\_SUGGESTIONS\_ACCEPTED}. An override is audited as \texttt{GRADE\_OVERRIDDEN}, and a regrade re-queues the answer and is audited as \texttt{AI\_REGRADE\_REQUESTED}.

\subsubsection{Login, Token Refresh, Logout and Password Change (M1; UC-01, UC-12)}
\begin{sloppypar}
In Figures~\ref{fig:seq_login} and~\ref{fig:seq_login_b} \texttt{AuthController} checks the salted PBKDF2 hash \cite{rfc8018} of the password (600,000 iterations of HMAC-SHA256, as the Open Worldwide Application Security Project (OWASP) recommends \cite{owasp_pwd}), the Student role, the HWID and the device binding (first bind, upgrade of a v1 binding, or \texttt{DEVICE\_MISMATCH}), then returns a JWT \cite{rfc7519} and a refresh token. Because each hash stores its scheme and cost, an older hash is re-hashed at the next login \cite{nist80063b}.
\end{sloppypar}

\begin{sloppypar}
Figure~\ref{fig:seq_login} covers the checks before the device binding. \texttt{LoginViewModel} reads the fingerprints and sends \texttt{POST} \url{/api/auth/student-login} with \texttt{usernameOrEmail}, \texttt{password}, \texttt{machineName}, \texttt{hardwareFingerprint} (v2) and \texttt{legacyHardwareFingerprint} (v1); \texttt{DeviceFingerprint} builds the v2 value from the raw string \texttt{"v2|BIOS|DISK|BOARD"}. \texttt{AuthController} looks up the user and its \texttt{DeviceBinding} by email or roll number and checks the password with \texttt{PasswordHelper.VerifyPassword}. Each \texttt{break} box ends the login: no user or a wrong password gives 401 \texttt{UNAUTHORIZED} with \texttt{LOGIN\_FAILED}, a non-student role gives 401 \texttt{FORBIDDEN}, and a missing fingerprint gives 400 \texttt{BAD\_REQUEST}, ``HWID is required for student login.'' The re-hash step runs only when \texttt{NeedsRehash} is true.

The call is \texttt{ApiClient.SaveAnswerAsync(sid, \{questionId, text, revision\})} to \texttt{POST} \url{/api/exams/sessions/{sid}/save-answer}. The server answers 404 when the session is not the caller's own, 400 ``Exam time is over'' after the deadline (exam end plus \texttt{ExtraMinutes} plus a 2-minute grace, by the server clock), 400 when the session is not InProgress, and 409 \texttt{STALE\_REVISION}. \texttt{OfflineSaveQueue.Classify} maps 2xx to Accepted and 409 \texttt{STALE\_REVISION} to Stale; no reply, 401, 408, 429 and 5xx to Offline, which is queued; and anything else to Rejected, shown as ``Not saved: ...'' and dropped from the queue but kept in the local backup. The queue keeps the newest revision per answer and is flushed after the 5-second \texttt{OfflineRetryDelay}; delivered and rejected saves leave the queue, and the first Offline stops the flush. The backup is AES-256-GCM with a DPAPI-wrapped key.
\end{sloppypar}

\subsubsection{Submission, Configuration and Report Export (M6, M8, M12; UC-08, UC-13, UC-18, UC-21)}
\begin{sloppypar}
On submit (Figures~\ref{fig:seq_submission} to~\ref{fig:seq_submission_c}) the client first flushes unsent saves; while one is still offline the window stays open. The server checks that the session is the caller's own and in progress, then in one save sets it to Submitted with the receipt hash and stores the staged grades, the plagiarism pairs and the \texttt{SESSION\_SUBMITTED} audit entry; it then queues the coding answers. The client verifies the receipt and releases the lockdown.

A save refused after the deadline is Rejected and dropped, so it does not block the submit; only a save that is still offline does, which is the \texttt{break} box. When offline, an automatic submit retries every 10 seconds and a manual one asks the student to press Submit again. Otherwise the client calls \texttt{POST} \url{/api/exams/sessions/{sid}/submit}, and the server checks the desktop token (\texttt{SeatGuard.DesktopRequired}), returns 404 for a missing or foreign session and 400 when the session is not InProgress.

\subsubsection{User Management and Eligibility (M7, M9; UC-20, UC-23, UC-25, UC-27)}
\begin{sloppypar}
Administrators manage accounts on the Users page through \texttt{UsersController}. An account is created on its own or in a batch that the page parses from a CSV file; the server skips each bad row with its line and reason and audits the batch as \texttt{USERS\_IMPORTED} (Figures~\ref{fig:seq_users} and~\ref{fig:seq_users_b}). When an Admin creates or acts on an Admin or SuperAdmin account, a single-account call is refused with 403 \texttt{SUPERADMIN\_REQUIRED} and a \texttt{PRIVILEGED\_ACCOUNT\_DENIED} entry is saved at once, while such a row in an import is skipped.
\end{sloppypar}

\begin{sloppypar}
In Figure~\ref{fig:seq_users} the page sends \texttt{POST} \url{/api/users} with \texttt{\{name, email, password, role, rollNumber\}}, where a roll number is entered for a student. The \texttt{alt} box lists the outcomes from top to bottom. A role that fails \texttt{Enum.IsDefined} gives 400 ``Unknown role.''. \texttt{GuardPrivilegedAsync("create", role)} gives 403 \texttt{\{code: SUPERADMIN\_REQUIRED\}} and saves \texttt{PRIVILEGED\_ACCOUNT\_DENIED} at once through \texttt{AuditService.LogAsync}. An email or roll number already in use gives 409 Conflict. Otherwise \texttt{PasswordHelper} makes a salt and a PBKDF2 hash at 600,000 iterations, \texttt{USER\_CREATED} is staged and sealed in the same \texttt{SaveChanges} as the user, and the reply is 201 Created \texttt{\{userId, name, email, role\}}. The page offers the Admin and SuperAdmin roles only to a SuperAdmin, and the API check also stops a direct call. \texttt{PUT} \url{/api/users/{id}} (\texttt{USER\_UPDATED}) uses the same guard, and an invalid roll number there gives 400.
\end{sloppypar}
